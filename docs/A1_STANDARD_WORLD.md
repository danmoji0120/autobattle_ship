# A-1 — P10 통합 기준 월드

로드맵 v2의 A-1. 지금까지 개별 플래그로만 켤 수 있던 시스템을 하나의 표준 월드로 묶어, 실제 서버가 새 월드를 만들 때 그 기준을 쓰게 한다.

## 1. 플레이어가 겪는 변화

- 서버가 새 월드를 만들면(빈 저장소에서 처음 시작할 때, 운영자 `WORLD_RESET` 때) **P10 우주: 40개 성계와 6개 세력**이 만들어진다. 영토와 탐사 안개도 함께 들어간다.
- 그 우주에서 다음이 **동시에** 동작한다.
  - 세력 경제 v2
  - P11 다자 전투·PvP
  - P12 함대 작전
  - P12.5 자동 물류
  - P13.1 잔해 인양
  - P13.2 약탈
  - P13.3 암시장
  - P13.4 치안·법 집행
  - P14 회사 신용도·세력 신뢰도
  - 기존 건설·생산·시장·조선·연구 (성장 월드 기본 기능)
- PMC 설립 화면이 실제 지급 조건을 서버에서 받아 보여준다.
  - 등록 정거장 이름과 운영 자금(성장 월드 12,000 cr)이 표시된다.
  - 이전 화면은 "운영 자금 7,000 cr"로 고정되어 있었다. 이는 성장 월드 이전의 금액으로, 실제 지급액과 달랐다.
- 이미 저장된 월드는 바뀌지 않는다. 프리셋은 **새로 만드는 월드**에만 적용된다.

## 2. 구현

| 위치 | 내용 |
|---|---|
| `src/world/worldPreset.ts` | `STANDARD_WORLD` 생성 옵션. `newWorldOptions(flags)`가 새 월드 생성 규칙의 단일 출처다. `worldRules(state)`는 월드가 실제로 돌리는 규칙을 상태에서 읽는다(로그·검사용). |
| `src/server/core.ts` | `ServerOptions.worldPreset` 추가. 빈 저장소에서 시작하면 `newWorldOptions(opts)`로 생성한다. |
| `src/server/node.ts` | 환경 변수를 한 번만 읽어 `worldFlags`로 만든다. 최초 시작(GameServer)과 `WORLD_RESET`이 같은 `worldFlags → newWorldOptions`를 쓴다. 시작 로그에 `rules={…}`를 남긴다. |
| `src/world/sim.ts` | `starterTerms()`: 새 회사가 받을 자금과 정거장. `createPlayer`와 같은 상수를 쓴다. |
| `src/server/protocol.ts`, `src/client/net.ts`, `src/client/app.ts`, `src/client/account.ts` | `needPmc`에 `start`를 실어 PMC 설립 화면에 표시한다. 구버전 서버가 값을 보내지 않으면 금액을 약속하지 않는 문구로 표시한다. |

### 환경 변수

- `WORLD_PRESET=standard`(기본값): 통합 표준 월드.
  - `COMBAT_P11`, `LAW_P134`, `REPUTATION_P14` 등 개별 기능 플래그는 새 월드 생성에 쓰이지 않는다.
  - 개별 플래그가 설정되어 있으면 시작 로그에 그 사실을 남긴다.
- `WORLD_PRESET=legacy`: 이전 동작(P9 배치, 개별 플래그 opt-in).
- 그 밖의 값: 서버가 월드를 쓰기 전에 오류로 종료한다.
- `REPUTATION_P14_MIGRATE`, `CONTENT_MIGRATE`, `ECON_MIGRATE`는 **기존 저장**을 변환하는 플래그로, 프리셋과 무관하게 그대로 동작한다.

### 발견해 고친 결함

- `WORLD_RESET` 경로에는 `REPUTATION_P14`가 빠져 있었다.
  - 그래서 `REPUTATION_P14=1`이어도 리셋한 월드는 평판 규칙 없이 만들어졌다.
  - 이제 두 경로가 같은 함수를 쓰므로 이런 불일치가 생길 수 없다.
- PMC 설립 화면의 지급 금액 표기 오류(7,000 → 실제 12,000).

## 3. 기존 기능과의 연결

- 각 시스템의 버전 게이트(`combatV`, `opsV`, `logisticsV`, `salvageV`, `piracyV`, `blackMarketV`, `lawV`, `repV`, `factionEcon`)는 그대로다. 프리셋은 이 게이트를 모두 켠 상태로 월드를 만들 뿐이며, 각 시스템의 규칙 자체는 바꾸지 않는다.
- 클라이언트는 상태에 실린 버전으로 UI를 고르므로, 표준 월드에서는 다음이 자동으로 나타난다.
  - 신용도 HUD
  - 평판·관계 탭
  - 세력 표시
- 계정은 월드와 분리된 저장소(DB 또는 `accounts.json`)에 있다. 리셋 뒤에도 로그인이 유지되고, 각 계정은 PMC 설립을 다시 받는다. A-2의 계정 정책과 일치한다.

## 4. 결정 필요 사항 (보고)

1. **운영 서버 기본값이 standard로 바뀐다.**
   - 운영 서버의 현재 저장 월드에는 영향이 없다.
   - 다음에 `WORLD_RESET`을 하거나 저장소가 비면 표준 월드가 만들어진다.
   - 운영 배포와 리셋은 이 작업에서 수행하지 않았다(승인 필요).
2. **가치사슬 가격(`ECON_PRICING=chain`)은 표준에 넣지 않았다.**
   - 로드맵의 통합 목록에 없고, 미승인 기본값으로 남아 있는 가격 방식이기 때문이다.
   - 넣으려면 `STANDARD_WORLD`에 `econ: 'chain'` 한 줄을 추가하면 된다.
3. **싱글플레이(브라우저 내 서버)는 여전히 P9 월드다.**
   - `src/client/net.ts`의 GameServer가 프리셋 없이 만들어지기 때문이다.
   - 로드맵 A-1이 "실제 서버"를 대상으로 하므로 바꾸지 않았다.
   - 싱글플레이도 표준으로 할지는 결정이 필요하다. 표준 월드는 틱 비용이 더 커서 배속 플레이에 영향이 있다(5절 참조).

### 6.1 표준 월드가 더 무거운 원인과 개선

V8 샘플링 프로파일러로 1시간 진행 뒤 10분을 측정했다(`scripts/a1/a1-profile.ts`, `artifacts/a1/profile-before.json`).

- 표준 월드에서 새로 켜지는 시스템의 비용은 작다. 게임 1초당 기준이다.
  - 함대 작전 0.19 ms
  - 인양 0.16 ms
  - 전투 권한 0.13 ms
  - 잔해 0.11 ms
  - 약탈 0.09 ms
  - 세력 경제 v2 0.05 ms
  - 영토 0.05 ms
- 비용의 대부분은 두 월드 공통의 함선 처리다. P10 배치 전용 월드와 표준 월드 모두 같은 함수가 가장 크다.
  - `hullEcon` 15~17%
  - `nearestHostile` 14~15%
  - `behave` 9~10%
- 표준 월드가 P10보다 약 1.3배인 것은 활동하는 함대·작전이 더 많기 때문이다. 특정 시스템이 과도하게 비싼 것은 아니다.

개선(`src/world/hullops.ts`):
- `hullEcon` 캐시를 문자열 키 조립 대신 두 단계 Map 조회로 바꿨다. 이 함수는 매 틱 모든 함선에서 호출된다.
- `yardHulls`(공영 조선소 판매 선체 목록)를 정거장 id와 조선 함급 기준으로 캐시했다.
- 콘텐츠 레지스트리는 프로세스 수명 동안 고정이라 캐시는 무효화가 필요 없다.

| 월드 | 수정 전 ms/게임 1초 | 수정 후 | `hullops.ts` 비용 |
|---|---|---|---|
| P10 배치 전용 | 11.81 | 9.78 (−17%) | 2.71 → 0.60 ms |
| 표준 | 15.76 | 12.51 (−21%) | 3.30 → 0.67 ms |

- 측정 조건: 두 측정 모두 다른 시뮬레이션이 동시에 돌던 같은 조건에서 했다. 그래서 절대값은 6절 표보다 높을 수 있고, 비교는 상대값으로 본다.
- 동작 불변 검증(`scripts/a1/a1-determinism.ts`, `artifacts/a1/determinism.json`):
  - 표준 월드 2개 시드에서 3개 회사가 채굴하며 1시간 진행한 저장 해시를 비교했다.
  - 수정 전후 해시가 비트 단위로 같았다.
- `nearestHostile`(그룹 수에 비례하는 적 탐색)은 바꾸지 않았다.
  - 틱 안에서 위치 계산 순서가 바뀌면 전투 결과가 달라질 수 있다.
  - 현재 비용(게임 1초당 약 2 ms)은 문제 수준이 아니다.

**발견한 기존 동작: NPC 전투의 실제 시간 예산.**
- NPC끼리의 전투는 틱마다 실제 시간 예산(`NPC_BATTLE_BUDGET_MS`) 안에서만 진행된다(`sim.ts`, 설계 주석에 명시).
- 서버가 바쁘면 전투 결과는 같지만 끝나는 게임 시각이 늦어진다. 그래서 같은 시드라도 부하에 따라 월드 상태가 달라진다.
- 결정성 검사는 시계를 고정해 이 효과를 없앴다.
- 같은 이유로 `tests/faction-econ2.test.ts`의 "cycle grid does not depend on the tick length"가 부하가 큰 상태(창업 시뮬레이션 2개 동시 실행)에서 실패했다.
  - 이 테스트는 서로 다른 스텝 크기의 두 월드 수입을 비교한다.
  - 단독 실행으로는 통과했다.
  - 기록: `artifacts/a1/INVALID-vitest-full-2-under-load.log`
- 같은 실행에서 A-1 테스트의 30분 진행 사례가 60초 제한을 넘었다. 진행을 15분으로 줄이고 제한을 180초로 늘렸다.
- 부하 없이 다시 실행한 최종 전체 회귀(최적화와 테스트 수정 후): 테스트 파일 88 통과(2 건너뜀), 테스트 896 통과, 16 건너뜀, 실패 0. 기록은 `artifacts/a1/vitest-full-3.log`.

## 7. 시작 자금과 초기 함선 운영비 (실제 초반 플레이)

`scripts/a1/a1-startup.ts`(`artifacts/a1/startup-std.json`, `startup-p9.json`)와 `scripts/a1/a1-comeback.ts`(`artifacts/a1/comeback.json`)로 측정했다. 새 회사 1곳, 시드 21·41, 6시간 진행이다.

### 7.1 숫자

시작 함대 운영비는 표준 월드 기준이다(`forecast`).

| 함선 | 편대 | cr/h (관리비 10% 포함) |
|---|---|---|
| 채굴선 mk1 ×2 | 제1 채굴반 | 385 × 2 |
| 구축함 mk1 | 경비대 | 825 |
| 초계함 mk1 ×2 | 경비대 | 330 × 2 |
| 보급품(화학약품 등) | | 94 |
| **합계** | | **약 2,349** |

- 시작 자금은 12,000 cr이므로, 아무것도 하지 않으면 **5.1시간** 버틴다.
- 운영비의 **63%(1,485 cr/h)가 경비대 전투함 3척**에서 나온다. 수입을 내는 채굴선 2척은 33%다.

시나리오별 6시간 결과다(두 시드가 거의 같아 시드 21 값을 적었다).

| 시나리오 | 표준 월드 | P9 월드 |
|---|---|---|
| 명령 없음 | 5.13h에 체납 시작, 6h에 체납 2단계(자금 0, 빚 2,026) | 5.18h 체납, 6h 2단계 |
| 채굴(케스트렐 → 아스트라 판매) | 수입 **25,908 cr/h**, 6h 후 152,757 cr, 체납 없음 | 18,222 cr/h, 106,778 cr |
| 채굴 + 경비대 호위 | 25,780 cr/h, 151,971 cr | 18,231 cr/h, 106,835 cr |
| 채굴 + 전투함 예비역 | 운영비 1,005 cr/h, 160,855 cr | 운영비 1,002 cr/h, 114,737 cr |

- 표준 월드의 첫 1시간 자금은 12,000 → 35,080 cr이다. 첫 채굴 한 번이면 운영비 문제는 사라진다.
- 채굴 수입은 운영비의 약 11배다. **채굴을 시작하는 플레이어에게 시작 자금·운영비는 문제가 아니다.**
- 표준 월드 수입이 P9보다 큰 이유는 채굴량이 같은 상태(29,269)에서 세력 경제 v2의 아스트라 매입가가 더 높기 때문이다. 별도 경제 검토 대상이다.
- P9 시드 41의 채굴+호위 실행은 채굴량이 같은데도 수입이 낮았다(12,925 cr/h). 원인은 아직 확인하지 않았다.

### 7.2 심각한 문제: 접속하지 않은 신규 회사의 진행 불능

새 회사를 만들고 접속을 끊은 플레이어가 10시간 뒤 돌아온 경우다(`a1-comeback.ts`).

- 복귀 시점: 자금 0, 빚 11,032 cr, **체납 4단계**.
- 채굴 명령은 수락되지만 모든 함선이 "운영비 체납 — 신규 출항 보류"로 정박해 있다.
- 이후 4시간 동안 채굴 0, 빚은 시간당 약 2,250 cr씩 늘어 20,052 cr이 되었다.
- 빚을 갚을 유일한 수입원인 채굴선이 출항하지 못한다.
  - NPC는 함선을 되사지 않는다.
  - 창고에 팔 물건이 없다.
  - 예비역 전환은 빚 증가를 늦출 뿐 갚지 못한다.
- 따라서 **다른 플레이어의 도움 없이는 회복할 수 없다.**

원인은 다음 셋이 겹친 것이다.
1. 시작 자금이 정박 상태 운영비 5.1시간분이다.
2. 체납 3단계(빚 발생 60분 뒤)는 정박 함선의 신규 출항을 막는다(`upkeep.ts departureHeld`). 그런데 채굴선의 출항이 곧 상환 수단이다.
3. 새 회사는 처음에 아무 작전도 갖지 않은 채 정박해 있다.

- 체납 3단계 진입 시점은 회사 설립 후 약 **6.1시간**이다. 밤새 접속을 끊는 일반적인 사용 패턴에 해당한다.
- 반대로 접속 중이든 아니든 설립 직후 채굴 명령을 한 번만 내리면 문제가 생기지 않는다(7.1).

이번 작업에서는 시작 자금과 유지비를 바꾸지 않았다(지시). A-3 창업 배경 설계에 넘기는 선택지는 다음과 같다.
- (a) 상환에 쓰이는 출항을 보류에서 제외한다. 예: 채굴·수송·납품 작전, 판매 목적 운항.
- (b) 새 회사에 운영비 유예 기간을 준다. 예: 첫 N시간 동안 체납 단계 진행 없음.
- (c) 창업 배경마다 시작 함대 구성과 비용 구조를 다르게 한다. 예: 운송업자는 수송선 중심, 경비업체는 전투함과 정기 계약.
- (d) 새 회사의 첫 편대에 기본 작전(가까운 광구 채굴)을 걸어 둔다.
- (e) 체납 4단계 회사에 탈출 수단을 준다. 예: NPC 조선소의 함선 매입, 긴급 계약.

이 중 (a) 또는 (b)는 창업 배경과 무관하게 모든 회사에 필요해 보인다. 결정은 사용자에게 보고한다.

## 8. 남은 사항

- **A-2**(월드 생성·운영 안정화): A-1의 생성·리셋 통합은 이미 완료됐으므로 중복 개발하지 않는다.
- **A-3**(세력별 창업 배경 시스템): 7.2의 진행 불능 문제를 함께 다뤄야 한다.
- 운영 서버에 적용하려면 배포 후 `WORLD_RESET=<토큰>`이 필요하다. 승인 전에는 수행하지 않는다.
