# 통합 회사 운영 시스템 (회사 본부 · 업무 · 결재)

브랜치 `feature/company-ops` (기준: `deploy/production` 41f29af). 운영 배포·운영 데이터 변경 없음.

## 1. 현황 조사와 발견한 문제

| 영역 | 기존 구현 | 문제 |
|---|---|---|
| 시설 건설 | `planOp`/`queueModule` 건설 큐, 자재 예약 (P95) | 회사 단위로 한눈에 볼 곳 없음 |
| 생산 | `ProdOrder` (`prodOrder`/`prodOp`, P963) | 목표(유지 재고)와 연결 없음 |
| 조선 | `ShipBuild` (`buildShip`/`buildOp`) | 〃 |
| 연구 | `ResearchProject` (`research`/`researchOp`) | 〃 |
| 수송 | 공용 배차 `LogisticsJob` + 정기 노선 `LogisticsRoute` (P981) | 화면이 물류 관리에만 있음 |
| 조달 | P982 자동 조달 (`procurement.ts`, 부족 자재 자동 구매) | 별도 예산·정책 → 승인 개념 없음 |
| 매매 | `buy`/`sell` 즉시 명령 | 기록 없음, 회사 손익 장부 없음 |
| 재고 | 정거장별 `storage` · 예약 · 선적 · 거래소 등록이 흩어짐 | 합계 화면이 없어 중복/누락 계산 위험 |

같은 역할의 엔진을 새로 만들지 않기 위해, **업무(work)는 기존 엔진 객체의 투영(projection)** 으로 설계했다.

## 2. 설계

### 2.1 업무 (`src/world/operations.ts`)
- 모든 유효 명령은 `WorldSim.command()` 래퍼에서 `registerCommand()`로 업무로 자동 등록된다.
  - 즉시 끝나는 명령(구매·판매·수리·장착·함선 구매·거래소)은 바로 `done` 기록. 승인 없음.
  - 지속 작업은 기존 엔진 ID에 연결: 시설(`module`), 생산(`ProdOrder`), 조선(`ShipBuild`), 연구(`ResearchProject`), 수송(`LogisticsJob`), 정기 노선(`LogisticsRoute`), 정거장 건립(그룹 found 작전 → 코어).
  - 진행률·상태는 매초 `projectWork()`가 원본 엔진에서 읽는다(이중 상태 없음).
- 제어(`workOp`): 일시정지/재개/취소/우선순위/수량/예산 → 기존 명령(`planOp`, `prodOp`, `buildOp`, `researchOp`, `poolControl`, `routeControl`, `setOp`)으로 변환. 목표는 하위 업무에 전파. 이미 선적된 화물은 취소하지 않음, 지출은 환불하지 않음.
- 보존: 끝난 업무 최근 200개, 업무당 로그 12줄.

### 2.2 회사 목표 (`workCreate`)
| 목표 | 동작 |
|---|---|
| `stockpile` (완료/유지) | 이송 → 생산 → 구매 순으로 계획. 이송은 다른 자사 정거장의 여유 재고(예약분 제외), 생산은 목표 정거장의 재고 주문, 구매는 위험·운송비 반영 최저가 시장. 생산 중이면 구매하지 않음(이중 구매 방지). |
| `trade` (반복 교역) | 매입 → 운송 → 판매. 실제 판매 대금/매입가 비율(`sellRatio`)을 학습해 손해 예상 시 대기. 2회 연속 손실 → 일시정지 + 손실 결재. |
| `fleet` | 최대 2척 병행 건조, 견적 = 선체 비용 + 조선소 수수료. |
| `facilities` | 한 번에 하나씩 건설. |
| `condition` | 가격 조건부 매수/매도(1회 또는 반복). |
목표는 일반 명령을 `withParent(goalId)` 안에서 발행하므로 하위 업무는 `parent`, `auto: true`로 기록된다.

### 2.3 권한과 결재
`authorize()` 판정 순서: 최소 보유 자금 → 시간당 지출 한도 → 예산 보유자(가장 가까운 상위 예산)의 단가 상한·한도 → 위임된 품목 자동 구매(`policy.autoBuy` + 위임 예산) → `autonomy='auto'` → `autoApproveBelow`(분할 우회 방지를 위해 **전체 필요량** 기준).
- 기본 정책은 `autonomy: 'ask'` — 승인 없이는 자동 구매하지 않는다.
- 결재 문서: 사유, 상황, 선택지(권장 표시), **추정**이라고 표기된 비용 견적, 위험(보안 등급 기반 추정), 거절 시 영향, 범위(이번만 / 이 목표 / 정책 위임 / 거절 / 수정 승인).
- 결재 피로 방지
  - 업무·사유별 1건만 유지하고 갱신(분할 요청 없음). 같은 작업의 여러 부족 자재는 한 건으로 묶음.
  - 거절 후 6시간 재요청 없음(비용이 1.5배 넘게 바뀐 경우만 재요청).
  - 상황이 해소되면 자동 종결. 하나를 승인하면 같은 업무의 다른 열린 결재도 종결.
  - 미결 결재는 해당 업무만 대기시키고 다른 업무는 계속 진행. 오프라인 중에도 서버 틱에서 진행.
- '이번만' 승인 한도 = Σ 수량 × ⌈단가 × 1.15⌉ (가격 변동 여유 15%).
- P982 자동 조달도 `procurementAuthority()`로 업무·목표 예산을 사용할 수 있다(기존 조달 정책은 그대로 유지).

### 2.4 장부(손익)
- `book()`: 시간별 버킷(48시간), 분류별 수입/지출, 품목별 매출.
- 명령 래퍼(중첩 기록 제외한 증감), `sellAt` 매출, 유지비(`stepUpkeep`, 판매 대금 공제분), 매초 잔차는 '기타'로 대사(`reconcileLedger`).
- 산업 손익은 **실제 판매 대금 vs 실제 지출**로만 판단한다(시세 기반 부가가치는 '추정'으로 별도 표시).

### 2.5 재고
`companyInventory()` (서버·클라이언트 공용 순수 함수): 합계 = 보관 + 예약(작업·건설 예약, 보관에서 빠진 분) + 운송 중(선적 화물) + 거래소 등록. 각 수량은 한 곳에서만 집계된다.

### 2.6 동기화·저장
- `works`, `approvals`는 소유자 전용 컬렉션(`sync.ts`의 OWNED). `Company.ops`는 공개 회사 뷰에서 제거됨.
- 저장 호환: 모두 **선택적(optional) 필드 추가**. 마이그레이션 없음. 기존 저장은 첫 틱에 기본 정책으로 초기화. 이전부터 있던 주문·건조 등은 '미등록' 상태로 기존 화면에서 계속 동작.

## 3. 회사 본부 패널 (`src/client/strategic/operationsUi.ts`)
상단 바 **회사 본부** 버튼(미결 결재 수 점 표시). 탭:
- **본부**: 핵심 지표, 목표, 긴급 문제, 결재, 최근 완료
- **업무**: 목표 등록 양식, 검색·필터, 상·하위 펼침, 제어(일시정지/재개/취소/우선순위)

- **산업**: 시설 가동률, 생산 주문, 병목, 부가가치(추정), 실제 매출

- **재무·결재**: 결재 문서(범위 선택·수정 금액), 시간별 장부, 매출 vs 유지비, 목표 예산, 정책 설정

## 6. 2차 구현 (같은 구조 위에서 완성)

### 6.1 지속 운영형 업무 — 함대 작전
- `WorkKind 'operation'`, `WorkMode 'continuous'`. 채굴·수송·순찰·호위·건설 작전은 지속 운영형, 이동·정박·공격·탐사·회수는 1회형.
- 그룹 작전 변경(`setOp`) 시 이전 작전 업무를 종결(지속형 → 완료, 1회형 → 취소)하고 새 업무를 연다. 진행 상태는 그룹 상태(`g.status`)·함선 유무에서 투영.
- 제어: 일시정지 = 작전을 `heldOp`에 보관하고 그룹을 대기로, 재개 = 보관한 작전 복원, 취소 = 대기. 모두 기존 `setOp` 명령으로 실행.
- 정거장 건립(`found`)은 기존대로 정거장 업무, 정기 노선이 운용하는 수송 그룹은 노선 업무로만 표시(중복 방지).

### 6.2 기존 저장 작업의 편입 (`adoptEngineWork`, 10초마다)
- 미등록 엔진 작업(미완성 시설·생산 주문·건조·연구·정기 노선·공용 배차·수행 중 계약·그룹 작전)을 `adopted: true` 업무로 만든다. 엔진 객체는 건드리지 않는다(재시작·중복 없음).
- 엔진 객체당 키(`workKeys`)로 이미 업무가 있으면 만들지 않는다. 조달(P982) 배차는 원래 생산/건설 업무의 하위 업무(`조달 · …`)로 편입.
- 1차의 '미등록' 표시는 '업무 편입 대기'로 바뀌었고, 다음 동기화 주기에 업무로 들어온다.

### 6.3 회사 전체 생산 계획 (`runStockpile` → `planProduce` / `planInputs`)
- 비축 범위: `scope: 'station'`(기본, 정거장 보관 + 입고 예정) / `'company'`(회사 전체 보유: 보관 + 예약·적재된 작업 화물). 둘은 별도 목표로 공존하며, 같은 범위·같은 품목 중복 등록은 거부.
- 계획 순서: ① 다른 자사 정거장 여유 재고 이송 ② 이미 계획된 생산량 차감 ③ 생산(레시피 1개 선택 → 최대 3개 정거장에 라인 수/(1+부하) 비례 분배, 작은 물량은 한 곳) ④ 중간재 계획(깊이 3, 부족분 = 필요량 − 회사 여유 재고 − 계획된 중간재 산출 − 소비 정거장으로 운송 중) ⑤ 남는 부족분만 구매.
- 중복 방지: 기존 목표의 개수형 주문은 `prodOp set`으로 늘리고 새 주문을 쌓지 않음. 다른 정거장에 있지만 수송선이 없어 옮길 수 없는 산출물도 '보류 재고'로 차감(과잉 생산 방지). 15분(900초) 진척 없는 주문은 '정체'로 표시해 대체 수단 판단.
- 회사 전체 목표가 묶어 둔 재고는 다른 목표의 '여유 재고'에서 제외(`goalHold`).

### 6.4 결재 — 실행 가능한 대안과 거절 후 검토
- 결재 문서 선택지: 승인(범위) / 다른 시장 최대 2곳(`market:<id>`, 비용 차이·거리·위험·도착 **추정**) / 자체 생산 켜기(`produce`) / 생산 시설 건설(`facility:<kind>`, 시설 비용 견적과 단가 비교) / 대기 / 거절. 각 선택지에 기대 효과·영향 문구.
- 거절 시 `reviewAfterReject`: 업무 로그에 "거절 후 대안 검토"를 남기고 대안만 담은 후속 결재 1건(`alt`)을 올린다. 그것도 거절하면 기록만 남기고 재요청하지 않는다(6시간 규칙 유지).
- 선택 결과는 실제 실행으로 이어진다: 시장 지정 → 해당 시장에서만 구매(위험 질문 생략), 시설 → 예산이 붙은 시설 목표 생성 + 24시간 구매 보류, 자체 생산 → 목표 `produce = true`.
- 조달 결재는 예산 보유자별로 묶어 1건(`inputs` / `purchase` 키)으로 올리고, 목표가 이미 계획한 중간재 산출량은 차감한다(가짜 부족 결재 방지).
- 결재가 막는 것은 그 업무뿐이다. 같은 회사의 다른 업무와 다른 회사는 계속 진행(§7 테스트로 확인).

### 6.5 패널 — 원인 → 해결 동작
- 진행 중이 아닌 업무마다 사유에서 해결 버튼(`fixes`)을 만든다: 결재 열기, 공용 수송선 지정, 시설 화면, 부족 원료 비축 목표, 창고·전력·연구·자금 화면, 함선 없는 작전 → 함대.
- 재고 표: 회사 총량 · 위치 · 가용 · 예약 · 운송 중 · 생산 예정 · 소비 예정 · 비축 목표 · 부족·잉여. 각 수량은 한 곳에서만 집계.
- 산업: 회사 생산 계획(목표별 주문), 주문별 병목과 해결 버튼(원료 비축·재고 보기·시설 추가·재개·결재). 연구: 정거장 연구 화면으로 이동. 물류: 공용 수송선 없음 경고 + 함대 작전 목록. 비축 목표 등록 양식에 범위 선택(`g-scope`).

### 6.6 저장 호환
새 필드는 모두 선택적(`Work.adopted`, `rt.heldOp/market/prod`, `GoalSpec.scope`). 마이그레이션 없음. 기존 저장은 다음 틱부터 편입·계획이 동작한다. 운영 데이터 변경·배포는 하지 않았다.

## 8. 산업 경제성 분석 (`scripts/industry-economics.ts`, 가격 변경 없음)

> **후속 분석으로 대체됨**: 이 절은 2차 작업 당시의 첫 분석이다. 비용 모델을 확장하고 실제 `WorldSim` 장기 실행과 개선안 비교를 한 결과는 [`INDUSTRY_ECONOMY_BALANCE.md`](INDUSTRY_ECONOMY_BALANCE.md)에 있다. 이 절의 CLI 인자(`<seed> <안정화 시간>`)는 `[안] [fresh|migrated] [seed] [json]`으로 바뀌었다.

`npx vite-node scripts/industry-economics.ts -- <seed> <안정화 시간>`. 실제 월드를 만들고 NPC 경제를 돌린 뒤, 레시피마다 최저 매입가 원료비, 최고 매도가(정거장 세금 포함, 50개 단위로 가격이 내려가는 실제 판매 규칙), 1시간 산출을 한 시장에 팔 때 평균가, NPC 장기 흡수량, NPC 구매 예산, 시설 자본비(건설비 + 자재 시가), 정거장 유지비(S급 100 cr/h의 ¼), 수송비(수송선 유지비 336 cr/h ÷ 450 적재)를 계산한다. 계산 규칙은 실제 명령과 대조했다: 구매 2,400 광석·판매 1,200 금속·880 합금의 예측 단가가 실제 거래와 6건 모두 일치(시드 5, 11).

### 8.2 판단
1. **광석 1차 가공이 지나치게 유리하다.** 원자재 0.25배 가격(`RAW_PRICE_V4`)은 c3→c4 마이그레이션(`migrate.ts`)이 그 시점에 시장에 있던 원자재 항목에만 적용한다. 새 월드에서는 처음부터 있던 철광석·크리스탈과 P9 정거장(`worldgen-p9.ts`)만 0.25배이고, 기존 정거장에 나중에 추가되는 규산염·가스·티타늄광·희토류광은 원래 가격이다(광석 기준가 2.3~4, 규산염 9, 가스 12~13.8, 티타늄광 18~20.7, 희토류광 49.5~56.3). 그래서 광석 정련은 시간당 약 1.4만 cr, 자본 회수 2~3시간인 반면 같은 단계의 실리콘·화학·희토류 정제는 시장 원료로는 손실이다. 의도한 차등인지 적용 누락인지 디자인 확인이 필요하다. 운영 저장의 실제 시장 기준가는 확인하지 않았다(운영 데이터 미접근).
2. **상위 공정은 수직 계열화가 전제다.** 기계부품·구조재·정밀부품·엔진·반응로는 시장에서 산 중간재로는 거의 이익이 없거나 손실이고, 하위 공정을 자가 생산할 때만 이익이 난다. 2차의 회사 전체 생산 계획(중간재 자가 생산)이 이 구조와 맞는다. 다만 상위 시설의 자본비(12만~71만 cr)가 커서 회수에 수십 시간이 걸리고, 엔진·반응로·센서는 NPC 수요가 라인 1~2개분밖에 안 된다.
3. **시장 깊이**: 1차 소재는 한 시장에 1시간 산출을 팔면 평균가가 시세의 73~83%로 내려간다(여러 시장 분산 필요). 상위 부품은 91~100%로 거의 영향이 없다. NPC 구매 예산(전체 회복 421,500 cr/h)은 대부분 레시피에서 라인 3~19개분이다.
4. **수송비는 작다**: 20분 운항 기준 원료 단위당 0.25 cr(배치당 3~15 cr)로 이익에 비해 무시할 수 있다. 위험(해적)에 의한 손실은 포함하지 않았다.
5. **가동 비용 구조**: 생산 자체에는 배치당 비용이 없고(노동비 `LABOUR_PER_S`는 함선 가격 평가에만 사용), 고정비는 정거장 유지비뿐이다. 그래서 일단 지은 시설은 거의 항상 가동하는 편이 이익이다.

### 8.3 가격을 바꾸지 않은 이유와 선택지 (디자인 결정 필요)
가격·비율 변경은 기존 저장(시장 기준가가 저장됨)과 진행 중인 경제 테스트에 영향을 주므로 적용하지 않았다. 선택지:
- (a) 다른 원자재에도 `RAW_PRICE_V4`를 일관 적용 → 실리콘·화학 정제가 이익이 되고 광석만 유리한 문제 완화. 기존 저장에는 c3→c4 경로와 같은 방식의 시장 기준가 마이그레이션 필요.
- (b) 1차 정련 산출 비율을 낮추거나 정련 시간 증가 → 광석 정련의 과도한 이익 축소.
- (c) 상위 시설 자본비 조정 또는 NPC 상위 부품 수요 증가 → 상위 공정 회수 기간 단축.
어느 쪽이든 이 스크립트와 `scripts/econsim.ts`로 전후를 비교한 뒤 적용해야 한다.
