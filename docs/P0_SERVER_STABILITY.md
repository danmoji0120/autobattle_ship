# P0 서버 안정화 · 성능 개선

장시간 운영과 동시 접속에 대비해 서버의 안정성·성능·데이터 보존을 개선했다. **게임플레이 규칙, 밸런스, 저장 데이터의 의미는 바꾸지 않았다.**
대상 운영 환경은 OCI E2.Micro(공유 2 vCPU, RAM 약 1GB, 스왑 2GB), Ubuntu 24.04, Node 22, Caddy, Supabase PostgreSQL이다.

## 1. 원인과 변경 요약

| 영역 | 원인 (기존 동작) | 변경 |
|---|---|---|
| 상태 동기화 | 매초 접속자마다 보이는 월드 전체를 새로 만들어 직렬화했다. 비용과 전송량이 접속자 수 × 월드 크기로 증가했다. 명령 1건마다 전원에게 전체 스냅샷을 다시 보냈다. | **프로토콜 2**(`src/server/sync.ts`). 엔티티 직렬화는 프레임당 가시성 변형별로 1회만 하고 모든 클라이언트가 공유한다(이전 프레임과 같으면 문자열 재사용). 각 클라이언트에는 이미 가진 상태와의 차이만 보낸다: 새/교체 엔티티, 필드 단위 패치(2단계 깊이), 함선 운동학 압축 배열, 삭제, 필요 시 키 순서. 명령 결과는 명령한 클라이언트에게만 즉시(최대 초당 10프레임으로 묶음) 보낸다. |
| 이동 패킷 | 0.2초마다 접속자별로 전체 함선을 훑어 행을 만들었다. | 같은 성계를 보는 클라이언트는 행 묶음 문자열을 공유한다. 자기 함선 중 다른 성계에 있는 것만 따로 덧붙인다. |
| 개인정보 | 기존 `snap` 경로의 규칙: 다른 회사의 창고·화물·물류·조달·사이트 스캔은 보내지 않는다. | 규칙은 한 곳(`legacyView`와 동일 함수)에 두고, 프로토콜 2는 버킷(공개/소유자/회사별)으로 분리한다. 동등성 테스트로 클라이언트가 받는 상태가 원래 코드의 결과와 **완전히 같음**을 검증했다. |
| WebSocket | 메시지 크기 제한 없음(ws 기본 100MiB). 속도 제한 없음. 느린 수신자 처리 없음. **소켓 `error` 리스너가 없어 잘못된 프레임 하나로 서버 프로세스가 종료됨**(재현함). | `src/server/wsguard.ts`와 `node.ts`: maxPayload 64KiB, 연결별 토큰 버킷(전체·명령·분석 질의), 폭주 시 연결 종료, 송신 버퍼 기준 혼잡 시 주기 갱신 생략 후 지속되면 종료, ping/pong 하트비트, 계정당 소켓 상한, 오류 리스너, 메시지 형식 검사. |
| 저장 | 저장마다 `JSON.parse(serialize())` 후 다시 `JSON.stringify`. analytics(최대 8MB)를 30초마다 월드와 함께 직렬화·전송했다(analytics 크기 계산까지 포함하면 같은 데이터를 4회 직렬화). 저장 실패는 콘솔에만 남았다. 종료 저장이 진행 중인 자동 저장과 겹칠 수 있었다. | `GameServer.saveText()`로 1회 직렬화한다(결과 텍스트는 기존 `JSON.stringify(snapshotFile())`와 바이트 단위로 동일). analytics는 같은 테이블의 `analytics` 행(파일 저장은 `*.analytics.json`)에 300초마다 저장한다. 실패·지연·중첩·펜싱 상태를 추적한다(`src/server/saver.ts`). 종료 시 월드를 먼저 멈추고 진행 중인 저장을 기다린 뒤 최종 저장한다. |
| 관측 | `/health`만 있었다. | `/health`는 그대로 두었다. 공개 `/ready`(대략적인 상태만), 운영자 전용 `/status`, 60초 주기 상태 로그를 추가했다. |
| logisticsJobs | 완료·취소된 작업이 영구 누적된다. | 보존 정책을 구현했지만 **기본은 꺼둠**(`LOGISTICS_JOB_RETAIN`). 근거는 §5. |

### 프로토콜 호환
- 클라이언트는 `hello`에 `proto: 2`를 보낸다. `proto`가 없는 클라이언트(배포 직후 새로고침 전의 구 브라우저 탭, `scripts/mptest.mjs` 등 기존 도구, 테스트)는 기존과 같은 `snap` 전체 스냅샷을 받는다.
- 싱글플레이(`LocalTransport`)도 프로토콜 2를 쓴다(브라우저 내 JSON 텍스트).
- 메시지 형식: `{"t":"sd","at","speed","full"?,"s":{스칼라},"x":[삭제 키],"c":[새 컬렉션],"u":{컬렉션:{id:엔티티}},"p":{컬렉션:{id:패치}},"k":{함선id:[px,py,pz,vx,vy,vz,heading]},"d":{컬렉션:[id]},"o":{컬렉션:[서버 순서]}}`
- 재접속은 `enter` 시 전체 상태(`full:1`)로 시작한다. 서버가 혼잡해서 건너뛴 프레임은 다음 메시지에 누적 차이로 반영되므로 유실되지 않는다.

## 3. 운영 설정 (환경 변수)

모든 값은 선택이다. 기본값은 측정값보다 여유 있게 잡았다.

| 변수 | 기본 | 의미 |
|---|---|---|
| `WS_MAX_PAYLOAD` | 65536 | 클라이언트 메시지 최대 바이트. 실제 최대는 수 KB(가장 큰 명령은 함선 ID 목록, 함선 500척에 약 5KB). 초과하면 1009로 해당 소켓만 종료한다. |
| `WS_MSG_RATE` / `WS_MSG_BURST` | 30/s · 120 | 연결당 전체 메시지. 브라우저는 2초마다 ping을 보내고 명령은 클릭할 때 보낸다. |
| `WS_CMD_RATE` / `WS_CMD_BURST` | 10/s · 60 | 게임 명령(cmd, border, view, speed, bjoin, createPmc, hello). 초과분은 버리고 cmd에는 오류 ack를 보낸다. |
| `WS_QUERY_RATE` / `WS_QUERY_BURST` | 1/s · 6 | 분석 질의. |
| `WS_FLOOD_DROPS` / `WS_FLOOD_WINDOW_S` | 300 · 10 | 10초 동안 300건 이상 버려지면 연결을 종료한다(1008). |
| `WS_SEND_HIGH` | 524288 | 송신 대기가 이 이상이면 해당 클라이언트의 주기 갱신을 생략한다. |
| `WS_SEND_LIMIT` | 8388608 | 송신 대기가 이 이상이면 즉시 종료한다. 클라이언트는 재접속해 전체 상태를 받는다. |
| `WS_CONGESTED_MAX_S` | 60 | 혼잡이 이 시간 넘게 이어지면 종료한다. |
| `WS_SOCKETS_PER_ACCOUNT` | 4 | 계정당 동시 소켓 수. 초과하면 가장 오래된 소켓을 4409로 닫는다. |
| `WS_HEARTBEAT_S` | 30 | ping 주기. 응답이 없으면 다음 주기에 종료한다. |
| `ANALYTICS_SEPARATE` | (켜짐) | `0`이면 analytics를 기존처럼 월드 저장에 포함한다. |
| `ANALYTICS_SAVE_INTERVAL_S` | 300 | analytics 별도 저장 주기(최소 30). 크래시하면 이 시간만큼의 분석 기록은 공백(gap)으로 기록된다. 월드는 영향받지 않는다. |
| `SHUTDOWN_SAVE_TIMEOUT_S` | 60 | 종료 저장 대기 한도. systemd `TimeoutStopSec=90`보다 작아야 한다. |
| `STATUS_LOG_S` | 60 | 상태 로그 주기(0이면 끔). |
| `LOGISTICS_JOB_RETAIN` | (끔) | 회사별로 보존할 완료 물류 작업 수. §5 참조. |

기존 변수(`SAVE_INTERVAL_S`, `ANALYTICS_MAX_BYTES` 등)의 의미는 바뀌지 않았다.

## 4. 저장 호환 · 복구

- **월드 행 형식은 그대로다.** `siderarium_world` 테이블의 스키마 변경은 없다. 같은 테이블에 `id='analytics'` 행이 하나 추가될 뿐이다(`{v, seed, time, store}`). 기록 조건은 `main` 행의 세대(gen)가 이 인스턴스의 세대와 같을 때로, 기존 펜싱과 동일하다.
- **업그레이드**: 첫 시작 시 월드 행 안의 analytics를 그대로 사용한다. 별도 행이 처음 기록될 때까지는 월드 저장에도 analytics를 계속 포함하므로 사본이 없는 순간이 없다.
- **롤백**(이전 서버로): 이전 서버는 `analytics` 행을 무시하고 월드 행만 읽는다. 별도 행이 생긴 뒤의 월드 행에는 analytics가 없으므로, 이전 서버는 analytics를 새로 시작한다(월드·계정·세션은 영향 없음). 이후 다시 업그레이드하면 두 사본 중 더 최신 것을 고른다. 실제 서버 프로세스와 PostgreSQL로 검증했다.
- **월드 초기화(WORLD_RESET)와 analytics**: 별도 기록은 시드가 같고 월드 시각보다 미래가 아닐 때만 사용한다. 초기화된 월드에는 이전 기록이 붙지 않는다. 파일 저장소는 초기화 시 analytics 파일을 백업 이름으로 옮긴다.
- **analytics 공백**: 별도 기록이 월드보다 오래되었으면(크래시 등) 그 구간을 기존 `gaps` 메커니즘으로 기록한다. 통화량 대사(reconciliation)는 0으로 유지된다.
- **저장 실패**: 실패는 로그(`!!! 저장 실패 (n회 연속)`)와 `/status`(`save.consecutiveFailures`, `lastError`, `lastOkAgoS`)에 남는다. 2회 이상 연속 실패하면 `/ready`가 503을 낸다. 재시도는 다음 저장 주기에 하고, 복구되면 `저장 복구` 로그를 남긴다. DB가 내려가 있어도 게임 진행과 `/health`는 영향받지 않는다.

## 5. logisticsJobs 보존 정책 (기본 꺼짐)

- 완료·취소된 작업은 배차·조달·자산 평가에서 읽히지 않고(화물·예약이 0인 경우), 소유 회사의 물류 패널 이력과 "완료 작업" 개수 표시에만 쓰인다.
- 보존을 켜면 회사별로 최신 N개의 완료 작업만 남긴다. 다음 작업은 **절대 삭제하지 않는다**: 비종료 상태, 배정된 함선이 있음, 함선이 참조 중(`s.logisticsJob`), 예약·적재 화물이 정확히 0이 아님.
- 삭제해도 다른 기록은 바뀌지 않는다. 테스트에서 보존 정책을 켠 월드와 끈 월드를 같은 입력으로 돌렸고, 물류 작업 이력을 제외한 월드 전체가 동일함을 확인했다.
- 기본으로 끈 이유: 켜면 플레이어에게 보이는 이력과 "완료 작업" 수가 줄어든다(게임 화면이 바뀜). 작업 1건은 약 400바이트다. 현재 규모에서는 저장 크기에 주는 영향이 analytics보다 훨씬 작다. 활성화 여부와 N은 운영 판단 사항이다(제안: 회사당 200).

## 6. 관측

- `GET /health`: 기존 그대로(`{ok, time, players}`).
- `GET /ready`: 공개. `{ok, save: ok|failing|stale|fenced, overload}`. 정상이면 200, 아니면 503. 업타임 모니터용이다.
- `GET /status`: **운영자 전용.** 서버 머신에서 리버스 프록시를 거치지 않고 직접 요청하거나(`curl -s http://127.0.0.1:8080/status`, 루프백이면서 X-Forwarded-*/Forwarded/Via 헤더가 없어야 함), `ANALYTICS_ADMIN_ACCOUNTS`에 등록된 관리자 계정으로 로그인한 세션이어야 한다. 그 밖에는 404를 반환한다. 내용: 틱 p50/p95/p99/max(최근 1분), 50ms 초과 횟수, 시뮬레이션 진행률, 이벤트 루프 지연, CPU, 메모리, 연결 수와 프로토콜, 송수신 바이트, 제한 동작 횟수, 저장 상태, 적용 중인 제한값. 비밀값·접속 문자열은 포함하지 않으며 저장소 호스트명은 가린다.
- 로그: 60초마다 `[siderarium] status tick p50/p95/p99/max … · loop p99 … · cpu … · rss … heap … · conns … · out … · save …`. 과부하이면 끝에 `OVERLOAD`가 붙는다.

### 지켜볼 지표
| 지표 | 정상 | 조치 기준 |
|---|---|---|
| `tick.p95` | 수 ms ~ 25ms | 50ms 초과가 지속되면 과부하(`overload`) |
| `tick.simRate` | ≈ 배속(1) | 0.9 미만이면 월드 시간이 실제 시간보다 느림 |
| `eventLoop.p99ms` | < 50 | 250 초과면 과부하 |
| `save.state` / `lastOkAgoS` | ok / < 2×저장주기 | `failing`·`stale`이면 DB 연결 확인 |
| `memory.rssMB` | 측정치 §7 | 기준선 대비 계속 증가하면 누수 의심 |
| `ws.floodClosed`, `ws.slowTerminated`, `ws.errors` | 0 또는 드묾 | 급증하면 악성 클라이언트 또는 네트워크 문제 |
