## 0. 요약

- **함재기 무장**: 함재기는 장비 아이템(`ArmContent`)이다. 새 하드포인트 종류 **H(격납고)**에 장착한다.
  - 조선·피팅·매매·인양·설계도는 기존 무장과 같은 경로를 탄다.
  - 별도 함선·소유권·전략 이동 체계는 만들지 않는다.
- **전투 중**: H 슬롯 하나는 함재기 정원만큼 비행체를 발진시킨다(비행대 하나 = H 슬롯 하나).
  - 비행체는 실제로 이동하고, 함선이나 비행체와 교전하고, 방공에 격추된다. 그 뒤 항모로 돌아와 재무장하고 다시 출격한다.
- **보충**: 탄약과 손실은 기존 무장처럼 **전투 단위로 처리한다**.
  - 매 전투는 정원을 꽉 채운 상태로 시작한다.
  - 전투 안에서는 격납고의 예비 기체 수(탄창과 같은 성격)만큼만 보충된다.
  - 전투 뒤에는 아무것도 남지 않는다. 새 자원 소모와 물류는 없다.
- **항모**: 기존 함선·피팅 체계를 그대로 쓴다.
  - H 하드포인트를 가진 선체와 **항공 장비 베이**(격납고 확장·관제·정비 모듈)로 다른 함선과 구별된다.
- **전투 엔진**: 비행체는 `World.ships`에 넣지 않고 **경량 비행체 풀**(구조 배열 + 공간 격자 + 비행대 단위 판단 + 기관포 즉시 판정)로 처리한다.
  - 규칙 3에서만 동작한다.
  - 함재기 무장이 없는 전투는 규칙 2와 비트 단위로 같아야 한다.
- **가장 큰 영향 지점**: 기존 코드 약 60곳이 "방공이 아닌 무장 = 포·미사일"이라고 가정한다(무장 `kind` 비교).
  - 해당 영역: 지휘관 AI 교전 거리, 전투 컴퓨터 사거리대, 전투력 평가, 검증기 무장 예산, UI 화력 표시.
  - 함재기는 새 무장 종류 `craft`로 두고, 이 지점을 전수 점검한다(§9.2).
- **구현 순서**: 성능 위험이 가장 크므로 첫 단계(P16.1)는 전투 엔진 시제품과 성능 측정이다.
- **사용자 결정이 필요한 사항**은 §13에 권장안과 함께 모았다.

## 3. 측정 — 비행체를 일반 함선으로 만들 때의 비용 (개정 1에서 유지)

측정 스크립트는 `scripts/p16/naive-perf.ts`, 원자료는 `docs/p16/naive-perf.txt`다.

- **조건**: 규칙 2, 40초. 이 컨테이너에서 1회 실행해서 경향만 본다.

| 소형함 n | 평균 ms/틱 | p95 | 최대 | 30Hz 예산 대비 | 최대 동시 탄체 |

| 0 | 0.29 | 0.74 | 4.2 | 1% | 105 |

| 200 | 3.14 | 7.22 | 12.0 | 9% | 4,121 |

**원인**

## 4. 바뀌지 않는 것 (전략층)

- 월드 저장 구조(`src/world/types.ts`): 새 필드가 없다.
- 함선 소유권·편성·이동·정박·조선 대기열·유지비·수리·전략 명령: 변경 없음.
- 함재기 무장 장비는 일반 무장과 같은 경로를 탄다. 창고에 보관하고, 피팅으로 장착하고, 격침되면 잔해로 남는다.
- 함재기의 전투 중 손실은 장비 손실이 아니다. 항모가 격침될 때 장착 장비가 잔해로 남는 기존 규칙만 적용된다.

월드 쪽에서 바뀌는 곳은 다음뿐이다.
- 전투력 평가(`src/world/combatRating.ts`): 함재기의 실효 화력을 반영한다.
- 경량 판정: `quickResolve`는 평가 수치를 쓰므로 위 변경을 따라간다.
- 상점 재고: 신규 월드는 카탈로그에 들어가고, 기존 월드는 이전 스크립트로 넣는다.

## 5. 데이터 모델 (제안)

### 5.1 함재기 무장

```ts
// schema.ts — 모두 선택 필드, 기존 팩 변경 없음
type HardpointType = … | 'hangar';                 // H 슬롯
interface WeaponStats {
  kind: … | 'craft';                               // 함재기: 발사체가 아니라 비행체를 발진시킨다
  craft?: CraftStats;
}
interface CraftStats {
  role: 'fighter' | 'bomber' | 'interceptor';      // 표적 선호: 함선 / 대형함 / 비행체·탄체
  n: number;            // 정원: 이 H 슬롯이 동시에 띄우는 비행체 수
  spares: number;       // 전투 1회 동안의 예비 기체 (탄창과 같은 성격; magMul·항공 모듈이 늘림)
  hp: number;           // 비행체 1기 HP
  speed: number; agility: number;          // 속도, 회피(맞히기 어려움)
  radius: number;       // 작전 반경: 항모에서 이 거리 밖으로는 나가지 않음
  sortie: number;       // 1회 출격 시간(초): 끝나면 귀환
  turnaround: number;   // 회수 후 재출격 준비(초)
  launch: number;       // 발진 간격(초/기)
  gun?: { damage: number; pen: number; range: number; reload: number };   // 즉시 판정 무기
  ordnance?: string;    // 대함 무장: 기존 WEAPONS id (missile·torpedo 탄체로 발사, 1출격 1회)
}
```

- **규칙**: H 하드포인트는 `craft` 무장만, `craft` 무장은 H 하드포인트에만 장착된다. 범용·미사일 하드포인트는 함재기를 받지 않는다.
- `armScore`(검증기 무장 예산)는 함재기에 맞지 않는다. 전용 점수를 둔다: 정원 × 출격당 피해 × 생존 보정. 크기별 기준값도 따로 둔다.
- **최소 콘텐츠 제안**: 함재기 무장 3종. 제작 재료는 기존 품목만 쓴다.
  - 전투기 비행대: 기관포, 함선·비행체 겸용
  - 뇌격기 비행대: 경어뢰 1발, 대형함 우선
  - 요격기 비행대: 비행체·미사일 요격

### 5.2 항모와 항공 장비

```ts
type InternalKind = … | 'flight';          // 항공 장비 전용 베이 (산업·컴퓨터 베이와 같은 방식)
interface ModuleContent { air?: AirSpec }  // 항공 모듈의 효과
interface AirSpec {
  complement?: number;   // 격납고 확장: H 슬롯마다 정원 +n
  spares?: number;       // 예비 기체 배율
  control?: number;      // 관제: 동시에 지휘할 비행대 수, 작전 반경 배율
  turnaround?: number;   // 정비: 재출격 준비 시간 배율
}
interface ShipFx { air?: AirSpec }         // 월드 → 전투 (shipFxOf가 모듈 효과를 합산)
```

- **항모 선체**: `SHIP_CLASSES`에 `carrier` 클래스와 기본 로드아웃을 추가한다(스커미시·실험실용).
  - 성장 콘텐츠에는 `HullDef` 1종(H 하드포인트 다수, 함포는 방공 위주, `flight` 베이 2~3개)과 설계도를 둔다.
  - 검증기는 모든 `HullDef.classId`가 `SHIP_CLASSES`에 있어야 한다고 검사한다(`validate.ts:81`).
- **항공 모듈 3종**: 격납고 확장, 관제 장치, 정비 설비.
- **관제 한도**: 관제 장비가 없으면 기본 한도만큼의 비행대만 임무를 받는다. 초과한 비행대는 항모 직위(CAP)에 머문다.
- **H 슬롯을 다른 함선에 줄지**(예: 전함 변형에 H 1개)는 콘텐츠 결정이다(§13-D5).

## 6. 전투 단위 보충 규칙

1. 매 전투는 H 슬롯마다 **정원만큼 발진 가능 + 예비 기체 수**로 시작한다. 이전 전투의 손실은 남지 않는다.
2. 격추된 기체는 예비가 남아 있으면 격납고에서 `turnaround` 뒤 새로 발진한다. 예비가 다 떨어지면 그 비행대는 줄어든 채로 싸운다.
3. 함재기 대함 무장(어뢰·미사일)은 출격 1회에 1회 발사한다. 귀환해서 재무장(`turnaround`)한 뒤 다시 쓸 수 있다. 전투 안에서는 탄약 제한이 없고, 출격·귀환 시간이 화력을 제한한다.
4. 항모가 격침되면:
   - 탑재 중인 기체는 함께 사라진다.
   - 공중의 기체는 남은 출격 시간 동안 싸운다. 회수할 항모가 없으면 출격이 끝날 때 전장을 이탈한다. 같은 진영의 다른 항모가 받아 주는 규칙은 §13-D6에서 정한다.
5. 전투가 끝나면 아무것도 저장하지 않는다. 함재기 무장 아이템은 항모가 살아 있으면 그대로 장착되어 있고, 격침되면 기존 규칙대로 잔해가 된다.

## 7. 항모 동작 (전투 중)

- **항모 컴퓨터** (`carrier` 원형, 규칙 3):
  - 적 함포 사거리 밖을 유지하면서, 자기 비행대의 작전 반경 안에 적이 들어오도록 거리를 잡는다.
  - 호위 그룹과의 이격을 제한한다.
  - 컴퓨터가 없는 항모는 기본 제어로 움직인다. 지휘관의 '예비대·사수' 명령과 비슷한 위치를 잡는다.
- **관제(비행대 임무 배정)**:
  - 2~4Hz로 비행대마다 임무를 정한다.
  - 임무는 CAP(항모 주변 방공), 공격(지휘관 표적 그룹), 호위(아군 대형함), 요격(접근하는 적 비행체·탄체).
  - 관제 한도를 넘는 비행대는 CAP를 맡는다.
- **지휘관 AI**: 함재기는 그룹의 '교전 거리' 계산에 넣지 않는다(§9.2). 지휘관의 표적 그룹 지정은 공격 임무 비행대가 따른다.

## 8. 전투 엔진 — 경량 비행체 풀 (규칙 3, 개정 1에서 유지·조정)

```
World
  ships[]            기존. 변경 없음
  craft: CraftPool | null   규칙 3이고 함재기 무장이 있을 때만 생성 (없으면 null: 기존 경로 그대로)
    squads[]         비행대 = (함선, H 마운트). 임무·표적·남은 예비·판단 타이머
    SoA 배열          x,y,z,vx,vy,vz,hp,state,squad,cool,sortie,tgt (Float32Array / Int32Array)
    grid             균일 공간 격자 (셀 ~250), 매 틱 재구성 O(n)
```

- **발진**: H 마운트 위치에서 `launch` 간격으로 나간다. 마운트가 치명타로 비활성(`disabled`)이면 발진·회수가 멈춘다.
- **판단은 비행대 단위**: 임무·표적은 2~4Hz로 정한다. 기체 단위에서는 대형 슬롯 조향과 공격 진입 상태 기계(접근 → 사격 → 이탈), 적분만 한다.
- **기관포 = 즉시 판정**
  - 사격 시점에 거리·각도·표적 크기·회피로 명중 확률을 계산하고, 결정론적 RNG로 판정한다.
  - **탄체 객체를 만들지 않는다.** §3의 탄체 폭증을 막는 핵심이다.
  - 함선에 맞으면 기존 `applyHit`을 거친다: 장갑 면·관통·구획 피해·치명타가 P15 규칙 그대로 적용된다.
  - 화면용 예광탄은 비행대 단위로 묶은 이벤트로 보낸다.
- **대함 무장**: 뇌격기의 어뢰와 미사일은 기존 `Munition`으로 발사한다. 함선 PD 요격·유도·구획 피해를 그대로 받는다.
- **함선의 대공**:
  - 규칙 3에서 PD는 요격할 탄체가 없거나 더 위협적인 비행체가 있으면, 공간 격자에서 사거리 안 적 비행체를 고른다. 판정은 즉시 처리한다.
  - 함포 포탄은 비행체에 충돌 판정하지 않는다(기존 탄체 루프 불변).
  - 대공 전용 무장(플랙)은 후속 콘텐츠다.
- **비행체 대 비행체·탄체**: 격자 이웃 질의로 처리한다. 요격기는 적 비행체와 유도 탄체를 노린다.
- **승패·철수**: 비행체는 진영 생존·가치 계산에 넣지 않는다. 함선이 모두 사라진 진영의 비행체는 전장을 이탈한다(§13-D7).
- **RNG 순서**: 비행체 풀은 함선 갱신 뒤에 같은 `rng`를 쓴다. 풀이 `null`이면 한 번도 뽑지 않는다.
- **결과**: `BattleResult`에 새 필드는 없다. 다만 통계(전투 기록·장교 경험치용 피해량)에 함재기가 낸 피해를 그 항모의 `dmgDealt`로 합산한다.

### 9.2 `kind` 가정 전수 점검 (가장 큰 위험)

- `src` 전체에서 무장 `kind`를 `pd`·`shell`·`missile`·`torpedo`와 비교하는 곳이 **약 60곳**이다(탄체 `kind` 제외).
  - 많은 곳: `sim/world.ts` 18곳, `render/battleView.ts` 9곳, `world/combatRating.ts` 8곳, `sim/ai/commander.ts` 6곳, `sim/ai/computer.ts` 5곳, `content/validateArsenal.ts` 4곳.
  - 나머지는 UI·레지스트리.
- 대부분 `kind !== 'pd'`를 "공격 무장"으로 읽는다. 예:
  - 지휘관 교전 거리 `dpsByRange`(`commander.ts:260`)
  - 전투 컴퓨터 사거리대 `bandsOf`(`computer.ts:104`)
  - 전투력 평가(`combatRating.ts:51`)
- `craft` 무장이 이런 곳에 섞이면 결과가 틀어진다. 지휘관이 함재기 작전 반경을 포 사거리로 오인하거나, 전투력이 이중으로 계산된다.
- **대응**:
  - `isGun(w)` / `isCraft(w)` 판별 함수를 두고 60곳을 하나씩 분류한다: 포격 의미 / 모든 무장 / 함재기 별도 처리.
  - 테스트(T5)에서 함재기 마운트가 있는 함선의 교전 거리·사거리대가 함재기를 뗀 같은 함선과 같은지 확인한다.

### 9.3 저장·리플레이

- **월드 저장**: 형식 변경 없음. 함재기 무장은 기존 장비 id 문자열로만 저장된다.
- **기록된 전투**: 자기 `rules`로 다시 돈다. 규칙 0~2 전투에는 함재기 무장이 있을 수 없다(콘텐츠가 없었다).
- 만약 규칙 2 이하 셋업에 `craft` 무장이 실려도, 그 마운트는 아무것도 하지 않는다.
- `BATTLE_RULES`를 3으로 올린다. 함재기 없는 규칙 3 전투 = 규칙 2 전투를 테스트로 고정한다.

## 10. 호환성 원칙 요약

1. 규칙 0·1·2 전투의 다이제스트가 바뀌지 않는다.
2. 함재기 무장이 없는 규칙 3 전투는 규칙 2와 다이제스트가 같다. 비행체 풀이 `null`이면 새 코드가 한 줄도 돌지 않는다.
3. 기존 월드 저장의 왕복 직렬화가 바뀌지 않는다.
4. 기존 하드포인트·베이의 장착 가능 목록이 바뀌지 않는다. 범용 하드포인트에 새로 허용되는 무장이 없다.
5. 기존 월드의 상점에 새 상품이 생기는 것은 이전 스크립트를 명시적으로 실행할 때뿐이다.

## 11. 성능 목표 (P16.1 합격 기준 제안)

이 컨테이너의 단일 전투, 함선 24척 핵심 구성(§3과 같음) 기준이다. 개정 1의 목표를 비행체 수로 그대로 쓴다.

| 구성 | 평균 | p95 | 최대 |
|---|---|---|---|
| 함선 24 + 비행체 200 | ≤ 1.5 ms | ≤ 3 ms | ≤ 10 ms |
| 함선 24 + 비행체 400 | ≤ 3 ms | ≤ 6 ms | ≤ 15 ms |
| 함선 60 + 비행체 800 (상한 확인) | ≤ 8 ms | ≤ 16 ms | ≤ 33 ms |

- 기존 P11 100·200척 하네스(`scripts/combat/perf.ts`)가 퇴행하지 않아야 한다.
- 서버 NPC 전투 부하 상한(`NPC_BATTLE_CAP` 160척)에 비행체 가중치(예: 1기 = 함선 0.25척)를 더한다.
- 렌더: 함재기 종류별 `InstancedMesh`. GPU 성능은 헤드리스 환경에서 측정할 수 없다(기존 한계와 같음).

## 16. 이번 개정에서 한 일과 하지 않은 일

**한 일**
- 방향 전환에 맞춰 문서를 다시 썼다.
- 추가로 분석한 코드: 하드포인트 장착 규칙(`rules.ts`), 무장 정의(`weapons.ts`), 모듈 효과 전달(`shipFxOf` → `ShipFx`, `magMul`), 무장 `kind` 가정 위치(약 60곳), 검증기 무장 예산(`validateArsenal.ts`).

**하지 않은 일**
- 코드 변경, 콘텐츠 추가, 테스트 추가, 배포.
- 비행체 풀의 실제 성능 측정. §11은 합격 기준 제안이다.

**유지한 측정**
- §3의 측정은 개정 1과 같은 1회 실행 결과다. 새로 측정하지 않았다.
