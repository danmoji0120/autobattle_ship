# P16.0 — F급 전투기·항모 체계 설계와 기존 코드 영향 분석

상태: **설계안 (구현 전)**. 이 단계에서는 기존 코드를 바꾸지 않았다. 새로 추가한 것은 분석용 측정 스크립트 `scripts/p16/naive-perf.ts`, 그 결과 `docs/p16/naive-perf.txt`, 그리고 이 문서뿐이다. 운영 서버에는 아무것도 배포하지 않았다.

## 0. 요약

- **목표**: F급 전투기를 일반 함선 체계(소유·제작·피팅·손상·손실)에 넣는다. 독립 비행대와 항모 탑재 비행대가 같은 데이터를 쓰게 한다.
- **결론 1 — 기체 하나를 함선 하나(`WShip`·전투 `Ship`)로 만들면 수백 기 규모를 감당할 수 없다.**
  - 측정(§3): 소형함 400척을 넣으면 전투 한 스텝이 평균 10.4ms, p95 21.6ms, 최대 41ms다. 30Hz 예산 33ms를 넘는 틱이 나온다.
  - 서버는 여러 전투를 동시에 돌리고, 클라이언트도 같은 전투를 다시 계산한다(락스텝). 그래서 이 수치는 그대로 쓸 수 없다.
- **결론 2 — 권장 구조는 "비행대 = 함선 1척 + 기체 명부"다.**
  - 비행대는 기존 `WShip` 한 척이다. 소유권·편성·이동·저장·동기화·매매·유지비 경로를 그대로 탄다.
  - 그 안에 기체(airframe)별 손상·상태 명부를 둔다.
  - 전투에서는 명부를 가벼운 비행체 풀(craft pool)로 펼친다. 함선 배열(`World.ships`)에는 넣지 않는다.
- **결론 3 — 항모가 하는 일은 '서비스 제공자' 공통 구조로 만든다.**
  - 탑재·발진·회수·정비·재무장·보충·관제를 이 구조 위에 올린다.
  - 같은 구조를 후속 수리선(정비 제공)과 보급함(보급 제공)이 그대로 쓴다.
- **결론 4 — 성능 위험을 먼저 확인한다.**
  - 구현 순서의 첫 단계(P16.1)는 전투 엔진 비행체 풀의 헤드리스 시제품과 성능 하네스다.
  - 성능이 데이터 구조(기체별 손상을 어디까지 개별로 둘지)를 결정하기 때문이다.
- **사용자 결정이 필요한 항목은 §13에 모았다.** 용어 충돌("편대"), 지구력 소진 시 처리, 항모 격침 시 탑재기 처리, 단독 비행대의 관문 통과 등이다. 각 항목에 권장안을 적었다.

## 1. 범위와 원칙 (요청 원문 정리)

| 원칙 | 이 설계에서의 의미 |
|---|---|

| 일반 함대에도 편성 가능, 항모 없이 장기 작전은 어려움 | 비행대는 일반 그룹(`WGroup`)에 속할 수 있다. 다만 **지구력(연료·탄약)**이 우주에 있는 동안 줄고, 항모나 정거장에서만 회복된다(§6.3). |
| 플레이어는 개별 기체가 아닌 비행대 단위로 관리 | 명령·피팅·편성·매매의 단위는 비행대다. 개별 기체는 손상 상태만 가진다. |
| 항모의 역할: 탑재·발진·회수·정비·재무장·보충·관제 | 항모 격납고 모듈이 서비스를 제공한다(§7). 관제는 전투 중 비행대 임무 배정이다. |
| 수리선·보급함까지 고려 | 서비스 제공자 공통 구조(§7.1). 이번 범위는 항모와 정거장만 구현한다. |
| 기존 함급·피팅·조선·저장·리플레이 보존 | 모든 새 필드는 선택 필드다. 월드 플래그로 켜고, 전투 규칙 3에서만 동작한다. 규칙 0~2 전투는 비트 단위로 같아야 한다(§9). |
| 대규모 전투에서 수백 기 운용 | 비행체 풀(구조 배열 + 공간 격자 + 비행대 단위 판단 + 기관포 즉시 판정, §8)로 처리한다. 성능 목표는 §10. |

### 2.2 그대로 쓸 수 없는 구조 (근거)

1. **전투 엔진의 함선당 비용이 함선 수에 대해 초선형이다.**
   - 무장 표적 선택(`chooseMountTarget`, `world.ts:847`)은 무장마다 0.3~0.55초 간격으로 **모든 함선을 순회**한다.
   - 탄체 충돌(`updateMunitions`, `world.ts:1094`)은 **탄체 수 × 함선 수**다.
   - 소형 고속 함선이 많아지면 기관포 탄체가 폭증한다(§3: 400척에서 동시 탄체 5,609개).
2. **함선은 탄약을 전투 단위로만 가진다.**
   - `magazineOf`(`world.ts:337`)가 전투를 시작할 때마다 탄창을 채운다. 전투 사이에 탄약 상태가 남지 않는다.
   - 재무장을 의미 있게 하려면 **비행대만의 지속 탄약 상태**가 새로 필요하다(§6.3).
3. **월드 함선의 상태값을 넓히면 영향이 크다.**
   - `WShip.state`(`'space' | 'docked' | 'battle' | 'building'`)를 22개 파일에서 125번 비교한다.
   - `Object.values(st.ships)` 순회가 월드 코드에 48곳 있다.
   - 그래서 `'embarked'` 같은 **새 상태값을 추가하지 않는다**(§5.3에서 대안 설명).
4. **전투기 크기 등급이 없다.**
   - `Size`는 S/M/L/XL이고, 무장·베이·정박 규칙이 모두 이 네 단계에 묶여 있다.
   - S 무장(기관포 등)을 전투기에 그대로 달면 초계함과 같은 화력이 된다.
   - `Size`를 넓히지 않고 **비행체 전용 장비 표시**로 구분한다(§5.1).
5. **렌더러가 함선마다 개별 메시 그룹을 만든다**(`src/render/shipMesh.ts`).
   - 수백 기를 그리려면 선체별 인스턴스 메시가 필요하다.
   - 인스턴싱 선례는 효과·소행성·BB-EX 판넬(`render/bbex/fx.ts`)에 있다.
6. **용어 충돌**: UI에서 "편대"는 이미 함대 그룹(`WGroup`)을 뜻한다(`client/strategic/hud.ts` 등 50곳 이상). 결정 사항은 §13-D1.

## 3. 측정 — "기체 = 일반 함선"의 비용

`scripts/p16/naive-perf.ts`로 측정했고, 원자료는 `docs/p16/naive-perf.txt`다.

- **구성**: 양측 전함 4 + 구축함 8에 소형함(초계함 강습형: 기관포 4 + PD 1)을 n척 더했다.
- **조건**: 규칙 2, 40초. 이 컨테이너에서 1회 실행했다.
- **한계**: 반복 측정이 아니므로 경향만 본다.

| 소형함 n | 전체 함선 | 평균 ms/틱 | p95 | 최대 | 30Hz 예산 대비 | 최대 동시 탄체 |
|---:|---:|---:|---:|---:|---:|---:|
| 0 | 24 | 0.29 | 0.74 | 4.2 | 1% | 105 |
| 100 | 124 | 1.37 | 2.71 | 5.7 | 4% | 2,010 |
| 200 | 224 | 3.14 | 7.22 | 12.0 | 9% | 4,121 |
| 400 | 424 | 10.38 | 21.57 | 41.1 | 31% | 5,609 |

**해석**
- 100척에서 400척으로 4배 늘면 평균 비용은 7.6배, p95는 8배가 된다.
- 서버의 NPC 전투 부하 상한은 `NPC_BATTLE_CAP` 160척, 예산 8ms다(`docs/P11_COMBAT_MULTISIDE.md`). 400기 규모 전투 하나가 그 예산을 넘는다.
- 클라이언트 관전도 같은 계산을 한다.
- 이 경로를 쓰면 실질 상한은 100~150기 정도다.

**전략층**
- 표준 월드에서 `WShip` 한 척의 JSON은 평균 458B다.
- 기체 300기를 각각 함선으로 두면 저장·동기화에 약 140KB가 늘고, 0.2초 이동 패킷도 300개 늘어난다.
- 비행대를 함선 1척 + 기체 명부(기체당 수십 B)로 두면 수 KB 수준이다(추정치, 구현 시 측정 필요).

## 4. 설계 선택지

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 기체 = WShip** | 기체마다 월드 함선. 비행대는 `WGroup` | 기존 코드를 가장 많이 그대로 쓴다. 기체별 피팅이 가능하다. | §3의 전투 비용. 저장·동기화·순회 비용이 기체 수에 비례한다. "편대 단위 관리"와도 어긋난다(목록에 기체가 수백 개). |
| **B. 비행대 = WShip + 기체 명부 (권장)** | `WShip` 1척이 비행대이고 `wing.af[]`에 기체별 상태를 둔다. 전투에서 비행체 풀로 펼친다. | 소유권·편성·이동·매매·저장·동기화를 그대로 쓴다. 전략층 비용은 비행대 수에 비례한다. 관리 단위가 요청과 같다. | 피팅 장비 수량·가치·유지비·수리·잔해를 '× 기체 수'로 고쳐야 한다(호출부 목록 §9.3). 기체마다 다른 피팅은 불가능하다. |
| **C. 별도 컬렉션 `st.wings`** | 함선과 분리된 새 엔티티 | 기존 함선 코드에 영향이 없다. | 소유권·이동·관문·정박·매매·동기화·관심 영역·저장 이전을 전부 새로 만들어야 한다. "일반 함선 체계에 추가"라는 원칙에 어긋난다. |

**권장: B.**
- 기체 명부는 **기체마다 손상(hp)과 상태만** 가진다.
- 피팅·선체·변형은 비행대에 하나다. 비행대 안의 기체는 같은 설계여야 한다.
- 이 균일성은 성능과 관리 단위 양쪽에 맞다. 다른 설계의 기체는 다른 비행대로 운용한다.

```ts
// schema.ts — 모두 선택 필드 (기존 팩은 변경 없음)
interface HullDef {
  /** 비행체 선체: 전투에서 비행체 풀로 펼쳐지고, 전략층에서는 비행대(WShip.wing)로만 존재한다 */
  craft?: CraftSpec;
}
interface CraftSpec {
  wingMax: number;          // 비행대 하나의 최대 기체 수 (예: 요격기 12, 뇌격기 6)
  deck: number;             // 격납고 점유 단위 (S 전투기 1, 중형 뇌격기 2)
  endurance: number;        // 항모·정거장 밖 작전 가능 시간(초)
  sortie: number;           // 전투 1회 출격 시간(초): 연료가 다하면 귀환
  agility: number;          // 회피 보정 (함선 evasion과 같은 의미)
}
type InternalKind = … | 'hangar';            // 항모 격납고 베이
interface HangarSpec {                        // ModuleContent.hangar (산업 장비 IndSpec과 같은 방식)
  deck: number;             // 탑재 용량(점유 단위 합)
  launch: number;           // 발진 속도 (기/초)
  recover: number;          // 회수 속도 (기/초)
  turnaround: number;       // 회수 후 재출격 준비 시간(초): 재무장·재급유
  repair: number;           // 탑재 기체 수리 속도 (hp 비율/분)
  control: number;          // 동시에 관제할 수 있는 비행대 수
}
interface EquipSpec { craft?: true }          // 비행체 전용 장비. 비행체 하드포인트에는 이것만 달린다.
```

- **전투 클래스**: `SHIP_CLASSES`에 `fighter` 클래스를 하나 추가한다.
  - 검증기는 모든 `HullDef.classId`가 `SHIP_CLASSES`에 있어야 한다고 검사한다(`validate.ts:81`).
  - 전략 수치(`ECON`)도 클래스 기준이라 이 항목이 필요하다.
  - 이 클래스로는 **전투에서 `Ship`을 만들지 않는다**. 규칙 3에서 비행체 풀로 바꾸는 것만 허용하고, 그 밖의 규칙에서는 전투에 넣지 않는다(§9.2).
- **비행체 장비**: 비행체 전용 기관포·대함 미사일·어뢰 무장을 `ArmContent`로 추가한다(`EquipSpec.craft: true`).
  - 비행체 하드포인트는 `craft` 장비만 받는다.
  - 일반 함선 하드포인트가 `craft` 장비를 받을지는 §13-D8에서 결정한다.
- **항모 선체**: 일반 `HullDef`에 `hangar` 베이를 둔다.
  - 경항모(순양함급)와 정규 항모(전함급) 두 등급을 제안하고, P16 첫 구현은 하나만 만든다.
  - 항모 피팅은 일반 피팅 화면을 그대로 쓴다.
- **최소 콘텐츠 제안**: 전투기 선체 1종(변형 2: 요격형·뇌격형), 항모 선체 1종, 격납고 모듈 2종, 비행체 무장 3종(기관포·대함 미사일·경어뢰).
  - 수량·수치는 P16.1 시제품의 성능·밸런스를 보고 정한다.

### 5.2 월드 상태

```ts
interface WShip {
  /** P16 비행대 (craft 선체만). 기체 명부 — 선체·변형·피팅은 비행대 공통 */
  wing?: WingState;
}
interface WingState {
  af: Airframe[];            // 생존 기체. 길이 = 기체 수 (0이 되면 비행대 소멸 = 함선 손실 처리)
  fuel: number;              // 남은 지구력(초). 항모·정거장에서 회복
  ordn: number;              // 남은 탄약 비율 0..1 (지속 상태, 재무장으로 회복)
  carrier?: string;          // 탑재 중인 항모 WShip id (없으면 독립 운용 중)
  reserve?: true;            // 예비 기체 묶음: 출격하지 않고 보충용으로만 쓴다
  mission?: WingMission;     // 기본 임무 (전투 관제: 'cap' | 'strike' | 'escort' | 'intercept')
  seq: number;               // 기체 일련번호 발급용
}
interface Airframe { id: number; hp: number /* 0..1 */; ready?: number /* 정비 완료 시각 */ }
```

- **소유권**: `WShip.owner` 그대로다. 기체는 비행대를 따른다. P16에서는 타사 항모에 탑재할 수 없다(§13-D9).
- **가치·유지비·수리**: 선체 1기 값 × 생존 기체 수다. 수리 견적은 기체별 (1 − hp)의 합이다.
- **`WShip.hp`의 의미**: 기존 화면과 정렬이 쓰는 대표값으로 **생존 기체 평균 hp**를 넣는다. 원본은 `af[]`다.

### 5.3 탑재 상태 — 새 `state` 값을 만들지 않는다

- 탑재 중인 비행대는 `state: 'docked'`, `task: { k: 'docked', station: <항모가 정박한 정거장> }`를 쓰지 않는다. 항모는 우주에 있을 수 있기 때문이다.
- 대신 **`state: 'space'` + `wing.carrier` + 항모 위치 추종**으로 표현한다.
- 이동·작전·교전 감지 코드에는 "탑재 중이면 건너뛴다"는 검사를 넣는다. 들어갈 곳은 함대 이동 `fly`, 교전 후보 `freeShips`, 동기화 이동 패킷, 작전 수행이다.
- 이 방식의 위험: 검사를 빠뜨린 경로에서 탑재 비행대가 혼자 움직이거나 혼자 교전한다. 대응은 §11-R3.
- **대안**: 탑재 비행대를 항모의 화물처럼 `st.ships`에서 빼고 항모 레코드 안에 넣는다.
  - 이러면 탑재 중에는 기존 함선 순회에 걸리지 않는다.
  - 대신 탑재·발진 때마다 엔티티가 생기고 사라져, 작업·물류·장교 연결이 끊긴다.
  - 그래서 권장하지 않는다.

### 5.4 전투 셋업

```ts
interface ShipSpec {
  /** P16 (rules ≥ 3): 비행대. 이 ShipSpec은 Ship을 만들지 않고 비행체 풀 하나가 된다 */
  wing?: { hp: number[]; ordn: number; fuel: number; carrier?: string /* 같은 셋업 안 항모의 ref */; mission?: WingMission };
}
```

- **결과**: `BattleResult`에 비행대별 생존 기체 hp 목록을 돌려준다. `ref`는 기존과 같이 `WShip.id`다.
- 격추 기체 수만큼 `af[]`에서 지운다.
- 항모에 탑재된 채 전투에 들어간 비행대: 셋업의 `carrier` 연결로 항모 안에서 시작하고, 항모 컴퓨터·지휘관이 발진 시점을 정한다.

## 6. 전략층 동작

### 6.1 생산·획득

- **자체 조선소**: `ShipBuild`에 `qty`와 대상(새 비행대 / 기존 비행대 `wing` id)을 둔다.
  - 야드 1 슬롯 하나에서 같은 설계 기체를 묶어 만든다.
  - 부품·장비는 수량만큼 소모된다(피팅 장비 × qty).
- **공개 조선소 판매**: 선체 `HullSale`을 그대로 쓴다. 단위는 기체이고, 산 기체는 새 비행대 또는 같은 설계의 비행대에 들어간다.
- **설계도·연구**: 기존 `BlueprintDef(target hull)`, `HullBuild.tech`.

### 6.2 비행대 관리 명령 (서버 검증)

| 명령 | 조건 |
|---|---|
| 분할 | 같은 위치. 새 비행대 `WShip`을 만들고 기체를 옮긴다. |
| 병합·보충 | 같은 선체·변형·피팅, 같은 장소(같은 항모 또는 같은 정거장), 합계 `wingMax` 이하 |
| 탑재 | 같은 회사의 항모, 거리 조건, 격납고 용량(`deck` 합) 이하 |
| 발진 | 탑재 중인 비행대를 항모 위치에 내놓는다. 이후 일반 그룹 명령을 따른다. |
| 피팅 변경 | 정거장 정비 시설 또는 항모 격납고. 장비 수량 = 기체 수 × 차이. 일부 기체만 바꾸려면 먼저 분할한다. |
| 매각·상장 | 기존 함선 매매 경로. 비행대 전체 단위 |

### 6.3 지구력 — "항모 없이 장기간 작전이 어렵다"의 구현

- **연료(`fuel`)**
  - 탑재 중도 정박 중도 아니면 1초에 1씩 준다.
  - 항모 탑재나 정거장 정박 중에는 회복된다. 회복할 때 항모 화물칸이나 정거장 창고의 연료 소모품을 쓴다(기존 `supplies` 구조).
- **탄약(`ordn`)**
  - 전투에서 쏜 만큼 줄고, 다음 전투는 남은 탄약으로 시작한다.
  - 재무장은 항모·정거장에서 하고, 탄약 소모품을 쓴다.
- **연료가 기준 이하(예: 25%)일 때**
  - 지휘관이 가장 가까운 아군 항모나 정거장으로 자동 귀환한다(P12 '복귀' 판단식 재사용).
  - 새 작전은 받지 않는다.
- **연료가 0일 때**: 처리 방식은 §13-D4에서 결정한다. 권장안은 최저 속도로 표류 귀환하고, 교전에 걸리면 전투력을 크게 깎는 것이다.
- **수치 예시**: 경전투기 `endurance` 20분이면, 성계 하나 안의 요격·호위는 가능하다. 여러 성계를 넘는 원정은 항모가 필요하다.

### 6.4 정비·보충

- **정비**: 탑재 중 손상 기체는 격납고 `repair` 속도로 회복한다.
  - 비용은 수리 견적식(§2.1)과 같다. 크레딧이 아니라 부품 소모로 할지는 §13-D10.
  - 정비 중인 기체(`ready > now`)는 출격하지 않는다.
- **보충**: 항모에 실은 **예비 비행대**(`reserve`)에서 같은 설계 기체를 옮긴다.
  - 예비 기체도 실제로 만든 기체이고 격납고 용량을 차지한다.
  - 정거장에서는 창고에 둔 예비 비행대에서 보충한다.

### 6.5 NPC

- P16 첫 구현에서는 NPC(연합·해적)에 비행대를 주지 않는다.
- 플레이어 비행대와 항모의 동작이 안정된 뒤 별도 단계에서 NPC 편성에 넣는다(P16.6).

## 7. 항모 서비스와 수리선·보급함을 위한 공통 구조

### 7.1 서비스 제공자

```ts
type ServiceKind = 'berth' | 'refuel' | 'rearm' | 'repair' | 'replenish' | 'control';
interface ServiceOffer { kind: ServiceKind; rate: number; range: number /* 0 = 탑재·정박만 */; supply?: string /* 소모 물품 */ }
// 제공자: 정거장(기존 services·시설), 항모(hangar 모듈), 이후 수리선(repair 모듈, range > 0), 보급함(supply 모듈)
function servicesAt(w: WorldState, s: WShip): ServiceOffer[];      // 이 함선이 지금 받을 수 있는 서비스 (제공자별 합산)
```

- **정거장**: 기존 `services.repair` / `refit`과 정비 시설을 `ServiceOffer`로 읽기만 하는 변환을 둔다. 정거장 동작은 바꾸지 않는다.
- **항모**: `hangar` 모듈이 `berth / refuel / rearm / repair / replenish / control`을 탑재 비행대에 제공한다.
- **후속 수리선**: 같은 그룹, 범위 안 함선에 `repair`를 제공한다. 일반 함선의 `hp` 회복.
- **후속 보급함**: `supplies`를 함대에 공급해 유지비 소모품을 창고 대신 화물에서 쓰게 한다. 이후 일반 함선에도 지속 탄약이 도입되면 `rearm`도 맡는다.
- 소모품 이동은 실제 화물 이동이다. 항모는 연료·탄약을 화물칸에 싣고 다니고, 바닥나면 서비스가 멈춘다.

### 7.2 관제 (전투 중)

- 항모의 `control` 값은 동시에 임무를 받을 수 있는 비행대 수다. 초과분은 기본 임무(CAP)로 움직인다.
- 관제 판단은 항모 그룹 지휘관과 항모 컴퓨터가 한다.
  - 위협 축 CAP, 적 대형함 공격(strike), 아군 대형함 호위, 적 비행체 요격.
- 독립 비행대(항모 없음)는 자기 그룹 지휘관의 판단만 받고 관제 보정이 없다.

## 8. 전투 엔진 — 비행체 풀 (규칙 3)

### 8.1 구조

```
World
  ships[]            (기존, 변경 없음)
  craft: CraftPool   (규칙 3 + 비행대가 있을 때만 생성; 없으면 null → 기존 경로 그대로)
    wings[]          비행대 단위: 팀, 그룹, 항모, 임무, 표적 그룹/함선, 남은 탄약·연료, 판단 타이머
    SoA 배열         x,y,z,vx,vy,vz,hp,state,wing,slot,cool,tgt (Float32Array/Int32Array)
    grid             균일 공간 격자 (셀 ~250), 매 틱 재구성 O(n)
```

- **판단은 비행대 단위**: 2~4Hz로 임무·표적을 고른다. 함선 지휘관 AI(`commander.ts`)처럼 그룹이 판단하고 개별 기체는 따른다.
- **기체 기동**: 비행대 기준점과 대형 슬롯을 향한 단순 조향에, 공격 진입(접근 → 사격 → 이탈) 상태 기계를 더한다. 기체마다 하는 일은 조향과 적분뿐이다.
- **기관포 = 즉시 판정**
  - 사격 시점에 거리·각도·표적 크기·회피로 명중 확률을 계산하고 결정론적 RNG로 판정한다.
  - **탄체 객체를 만들지 않는다.** §3의 탄체 폭증을 막는 핵심 장치다.
  - 화면용 예광탄은 이벤트(비행대·틱 단위로 묶음)로만 보낸다.
- **대함 미사일·어뢰**
  - 기존 `Munition`으로 발사하므로 함선 PD 요격·관통·구획 피해(P15)를 그대로 받는다.
  - 기체당 탄수가 적어 탄체 수는 제한된다.
- **함선이 기체에 입히는 피해**: 함선 기관포 탄체는 계속 함선만 맞춘다(규칙 불변). 함선의 대공은 아래 두 경로로만 한다.
  - **PD 무장**: 요격할 탄체가 없으면 격자에서 사거리 안 적 기체를 골라 사격한다. 판정은 즉시 처리한다.
  - **대공 전용 무장**(후속 콘텐츠): 원뿔 범위 안 기체 다수에 확률 피해.
- **기체 대 기체**: 격자 이웃 질의로 교전 상대를 고르고, 즉시 판정한다.
- **항모 발진·회수**
  - 항모 위치에서 `launch` 속도로 기체를 내보낸다.
  - 연료·탄약이 다하면 귀환하고, 회수 속도로 받은 뒤 `turnaround` 후 다시 출격한다.
  - 항모 피격으로 격납고가 손상되면 발진·회수가 느려진다(치명타 종류 추가, §13-D5와 연동).
- **결과**: 기체는 '생존 / 격추 / 이탈'이고, 함선 결과와 같은 방식으로 셋업 `ref`에 묶여 돌아간다.

### 8.2 기존 규칙과의 경계

- `World.ships`·`Group`·지휘관 AI·승패 판정은 기체를 보지 않는다.
- **승패**: 함선이 모두 사라지고 기체만 남은 진영은 패배로 본다(기체는 점령할 수 없다). 이 처리가 맞는지는 §13-D11.
- **진영 가치 비율**(`teamValueFrac`, 철수 판단): 기체 가치를 넣을지 정해야 한다. 권장은 넣되, 기체 가치 비중의 상한을 두는 것이다.
- **RNG 순서**: 비행체 풀은 함선 갱신이 끝난 뒤 같은 `rng`를 쓴다. 비행대가 없는 전투에서는 한 번도 뽑지 않으므로 기존 전투가 바뀌지 않는다(§12 테스트 T1·T2).

## 9. 호환성과 영향 범위

### 9.1 저장

- 모든 필드는 선택 필드다(`WShip.wing`, `ShipBuild.qty`, 콘텐츠 `craft`·`hangar`).
- 기존 저장에는 이 필드가 없으므로 그대로 읽힌다.
- 월드 플래그 `airV`가 켜진 월드에서만 비행대를 만들고 탑재 명령을 받는다.
- 표준 월드 프리셋에 넣을지, 기존 월드에 어떻게 적용할지는 P15.1과 같은 방식(카탈로그 추가 + 환경 변수 마이그레이션)으로 따로 정한다.

### 9.2 전투 리플레이

- 기록된 전투는 자기 `rules`로 다시 돈다. 규칙 0~2 전투에는 비행대가 있을 수 없다.
- `BATTLE_RULES`를 3으로 올려도, 비행대 없는 규칙 3 전투는 규칙 2와 같은 결과여야 한다(테스트로 고정).
- 규칙 2 이하 셋업에 `wing`이 실린 경우(있어서는 안 됨)는 비행대를 전투에 넣지 않고 그대로 귀환시킨다.

### 9.3 '× 기체 수'가 필요한 호출부 (구현 때 전수 수정 대상)

| 대상 | 위치 | 조치 |
|---|---|---|
| 실물 장비 수량 | `fittingItems` 호출 5곳 (`fitting.ts:57` 외) | 비행대면 기체 수를 곱하는 래퍼 하나로 통일 |
| 함선 가치 | `shipWorth` / `shipValue` 호출 30곳 | 비행대 가치 래퍼 (선체 값 × 생존 기체 수) |
| 유지비 | `shipRate` (`upkeep.ts:54`) | 기체 수를 곱한다 |
| 수리 | `repairQuote` (`repair.ts`) | 기체별 손상 합 |
| 전투력 평가 | `combatRating.ts` | 기체 수와 지구력 보정 |
| 경량 판정(란체스터) | `quickResolve` / `quickResolveP11` (`sim.ts:4571`, `4608`) | 비행대 전투력 반영, 기체 손실 분배 |
| 잔해 | `finishEngagementObserved` (`sim.ts:4652`) | 비행대별 소형 잔해 1개(격추 기체 수만큼 장비·고철) |
| 함선 순회 | `Object.values(st.ships)` 48곳 | 대부분 그대로 둔다(비행대도 함선). 탑재 중 건너뛰기가 필요한 곳만 표시(§5.3) |

### 9.4 동기화

- 비행대는 `WShip` 1개라서 관심 영역 규칙(`server/sync.ts:125`)을 그대로 쓴다.
- 기체 명부는 소유자에게만 전부 보내고, 다른 회사에는 기체 수만 보낸다(`publicShip`).
- 탑재 중인 비행대는 이동 패킷에서 뺀다. 위치는 항모를 따른다.

## 10. 성능 목표 (P16.1 시제품의 합격 기준 제안)

이 컨테이너의 단일 전투 기준이다. 비교 대상은 §3과 같은 함선 24척 핵심 구성이다.

| 구성 | 평균 | p95 | 최대 |
|---|---|---|---|
| 함선 24 + 기체 200 | ≤ 1.5 ms | ≤ 3 ms | ≤ 10 ms |
| 함선 24 + 기체 400 | ≤ 3 ms | ≤ 6 ms | ≤ 15 ms |
| 함선 60 + 기체 800 (상한 확인) | ≤ 8 ms | ≤ 16 ms | ≤ 33 ms |

- 비행대 없는 기존 전투(P11 100·200척 성능 하네스)는 이전 수치에서 퇴행하지 않아야 한다.
- **서버 부하 예산**: NPC 전투 상한(`NPC_BATTLE_CAP`)을 기체 가중치(예: 기체 1 = 함선 0.25)로 다시 정의한다. 기체가 많은 NPC 전투는 경량 판정으로 넘어간다.
- **렌더**: 선체별 `InstancedMesh`를 쓰고, 예광탄은 기존 파티클 풀을 쓴다. 브라우저 측정은 소프트웨어 렌더링이라 GPU 성능은 측정할 수 없다(기존 한계와 같음).

- 관련 코드 분석: 함급·콘텐츠 스키마·피팅·조선·유지비·수리·전투 연결·결과 반영·전투 엔진 비용 구조·동기화·렌더.
- 측정 2건(`docs/p16/naive-perf.txt`):
  - 소형함 대량 전투의 스텝 시간. 반복 없이 1회 실행했다.
  - 표준 월드의 함선 직렬화 크기.
- 이 설계 문서.

**하지 않은 일**
- 기존 코드 변경, 콘텐츠 추가, 테스트 추가, 운영 서버 배포.
- 비행체 풀의 실제 성능은 측정하지 않았다. §10의 목표는 측정이 아니라 합격 기준 제안이다.
- §3의 전략층 크기 비교(비행대 방식 수 KB)는 추정치다.

**확인된 문서·코드 차이**
- `docs/P15_1_COMBAT_COMPUTERS.md`는 항모 원형을 "데이터·확장 지점만 있음"으로 적고 있고, 코드(`computer.ts:16`)와 일치한다. 차이는 없다.
