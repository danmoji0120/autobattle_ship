## 1. 공개 방식 — 개발 플래그 (사용자 결정)

작업 중 다른 세션이 원격 브랜치에 개발 전용 플래그 방식의 커밋을 올렸다 (`f5cbbfd` … `cd188c8`). 나는 로컬에서 기본값 자체를 규칙 3으로 바꾸는 커밋을 만들어 두었기 때문에 두 방식이 충돌했다. 사용자는 **원격 플래그 방식 유지**를 선택했다.
- 내 로컬 기본값 공개 커밋은 버렸다. 로컬 브랜치 `backup/p166-local-release-ad7a227`에만 보존했고 푸시하지 않았다.
- E2E와 마이그레이션 검증은 플래그를 켠 상태로 수행했다.
- 이번 작업의 커밋은 검증 스크립트, 문서, 그리고 검증 중 발견한 결함 수정 1건이다.

공개 스위치 (`src/content/carrierRelease.ts`):

| 조건 | 결과 |
|---|---|
| 서버: `NODE_ENV=development` 이고 `P16_DEV_CARRIER_RELEASE=1` | 개발 공개 |
| 클라이언트: `vite --mode p16-dev` 이고 `VITE_P16_DEV_CARRIER_RELEASE=1` | 개발 공개 |
| 그 외 (운영 빌드, 일반 개발, 플래그 없음) | `BATTLE_RULES = 2`, 여명급 `preview`, 함재기·항공 모듈 생산·구매 차단 |

서버 보호 장치 (`src/server/node.ts`):
- 개발 공개 모드에서 `DATABASE_URL`을 쓰면 로컬 주소이고 `P16_DEV_TEMP_DB=1`이어야 한다. 그렇지 않으면 서버가 시작을 거부한다.
- `CARRIERS_P16_MIGRATE=1`은 개발 공개 모드에서만 허용된다. 운영 모드에서는 "운영 마이그레이션 미승인"으로 시작을 거부한다.

규칙 0–2로 저장된 전투와 리플레이는 각 기록의 `setup.rules`로 재생된다. 플래그와 무관하다 (§3, §5에서 확인).

## 2. 실제 월드 E2E

### 2.1 실행 방법

```
npm run build && npm run build:server
NODE_ENV=development P16_DEV_CARRIER_RELEASE=1 npx vite-node scripts/p16/e2e/carrier-server.ts
```

- 실제 서버(`dist-server/server.mjs`)와 표준 월드를 쓴다. 저장 파일은 임시 디렉터리에 둔다.
- 실제 WebSocket 계정 셋을 쓴다.
  - A 항모 PMC (경비 배경)
  - B 포격 PMC (퇴역 군인 배경, 상대)
  - C 인양 PMC (인양업자 배경)
- 서버를 멈춘 상태에서 한 번만 배치한 것 (`scripts/p16/e2e/scenario.ts`):
  - A의 후반 **비(非)항모** 상태: 자체 L 기지(연구소·공장·L 조선소 기반 시설), 일반 재화, 자금, 신용.
  - B의 포격 전대와 자금.
  - C의 운영 자금. 약 15시간 무수입이면 체납으로 출항이 보류되기 때문이다.
- 항모 관련 물건은 **하나도 배치하지 않았다.** 기술, 설계도, 선체, 함재기, 항공 모듈, 관제 컴퓨터, 요격기·포·PD는 모두 실제 명령(연구·구매·생산·건조·피팅)으로 얻었다.
- 연구·생산·건조에는 수십 시간이 걸린다. 이 구간은 서버를 멈추고 저장된 월드를 같은 `WorldSim` 갱신 루프로 진행시켰다(연구 11.5 h, 건조·생산 3.7 h). 다른 편집은 하지 않았다. 전투, 전투 중 재시작, 관전, 리플레이는 실행 중인 서버에서 진행했다.

### 2.3 실제 브라우저 관전 (`scripts/p16/e2e/browser-spectate.ts`)

- 배포 클라이언트(`dist/`)를 headless Chromium(SwiftShader)으로 열었다. C의 실제 세션 쿠키로 로그인하고 `#mpJoin`으로 공유 월드에 들어갔다.
- HUD의 "전투 관전" 경로(`onOpenBattle`)로 진행 중인 월드 교전을 열었다.
- 결과:
  - 규칙 3, 비행체 풀 있음, 페이지 오류 0.
  - 브라우저의 틱 346 다이제스트 = 서버 스트림(binit + orders)을 같은 틱까지 lockstep 재시뮬레이션한 다이제스트.
  - 틱 지연 표본 8개(서버 − 브라우저, 30틱 = 1 s): `[7, 37, 37, 62, 74, −1, −7, 11]`. 중앙값 37.
- 지연 판정 기준: 앞서지 않음(≥ −35), 중앙값 ≤ 60, 최댓값 ≤ 150.
  - 클라이언트는 1 s 주기 스냅샷 틱 + 최대 2 s 로컬 시간으로 진행한다(`battleLink.targetTick`). 기준 틱 자체도 당사자의 마지막 스냅샷이다. 그래서 개별 표본에는 1–2 s의 주기 잡음이 섞인다.
  - 14회차에서 한 표본이 96틱(3.2 s)이었다. 서버·WebGL 소프트웨어 렌더·하네스가 한 컨테이너에서 경쟁한 순간이다. 다음 표본은 7틱으로 돌아왔고 다이제스트는 같았다. 동기화 결함이 아니라 판정 기준(|지연| ≤ 90)이 지나치게 엄격했던 것으로 보고 기준을 위처럼 조정했다.

### 2.5 E2E 중 발견한 결함과 관찰

**결함 (수정, `31360a1`):**
- `src/world/sim.ts`의 `hullChoice`가 `hull.preview`를 직접 검사했다.
- 그래서 개발 공개 모드에서도 여명급 건조·구매가 거부됐다.
- `!hullReleased(hull)`로 바꿨다. 운영 모드 동작은 같다(`hullReleased`가 미공개 선체를 거부).

**관찰 (설계대로, 변경하지 않음):**
1. 공공 정비소의 `fit buy`는 정비 서비스 가격을 받는다. 시장 재고는 차감하지 않는다(지역 한정 고급 장비 제외). 시장 재고는 `buy` 명령에서만 줄어든다. 항모 장비도 같은 규칙을 따른다.
2. 전투기는 짧은 교전에서 귀환이 드물다. 전투기의 회수는 대부분 교전 후반에 일어난다.
3. 이 시나리오의 B 포격 전대(전함급 포함)는 여명급 항모단(항모 + 호위 3)을 손실 없이 이겼다. 시나리오는 흐름 검증용이다. 밸런스 판단 근거로 쓰지 않는다(동등 비용 비교는 `docs/P16_5_AIR_BALANCE.md`).
4. 시나리오 보정 2건 (코드 결함 아님):
   - 인양 회사 C를 전투 전에 helios로 옮겼다. 원래 위치인 세레스에서는 잔해 소멸 전에 도착하지 못한다(`salvzone`은 남은 시간이 이동 시간 + 30 s보다 짧은 잔해를 건너뛴다).
   - C에 운영 자금을 배치했다. 체납 상태면 신규 출항이 보류되기 때문이다(A-2.1).

## 3. 기존 월드 마이그레이션 검증

### 3.1 사용한 저장본

- **이 개발 환경에는 운영 저장본 사본이 없다.** 운영 DB에도 접속하지 않았다.
- 대신 `scripts/p16/e2e/mig-make.ts`로 **P16.6 이전 코드(`15de811`)의 실제 서버**가 만든 저장본을 썼다.
  - 표준 월드에 실제 계정 3개(운송·경비·인양 배경)를 만들었다.
  - 구 `WorldSim`으로 6시간 진행했다(NPC 경제·NPC 전투 → battleLog 30건).
  - 구 서버로 한 번 더 로드·저장했다.
- 규모: 회사 6(플레이어 3), 함선 175, 부대 41, 전투 기록 30(전부 규칙 2), 시장 239행.
- 운영 저장본으로 같은 검사를 다시 하려면 §8의 절차대로 사본을 만들어 `mig-verify.ts`에 넣으면 된다.

## 4. NPC 항모와 경량 판정

### NPC의 항모 획득·편성

- NPC 함대는 클래스·표준 로드아웃(`classId` + `loadoutId`)으로 만들어진다. 해적 은신처와 세력 순찰도 같다. 항모 클래스나 항공 로드아웃을 쓰는 NPC 생성 경로는 없다.
- 여명급에는 NPC 판매(`sale`)가 없다. 설계도로만 건조할 수 있다. NPC 회사는 연구·설계도 구매를 하지 않으므로 항모를 얻지 못한다.
- E2E 0단계에서 확인했다. 개발 공개 모드의 새 표준 월드에도 항모는 0척이다(NPC 포함).
- 결론: NPC 항모 운용은 검증되지 않았다. 지시대로 **첫 공개 범위에서 NPC 항모 자동 생성은 제한한다(현재 상태 유지).**

### 경량 판정 오차 (P16.5.1 측정, 24시드)

- 항모 대결 13종의 평균 절대 오차는 0.262다. 전체 20대결 평균은 0.228이다.
- 오차가 큰 사례는 다음과 같다.
  - 포격·미사일·순양 대체 함대는 경량 판정에서 같은 값(440)이다. 그러나 항모 함대 상대 실제 결과는 1.00 / 0.25 / 0.29다.
  - 뇌격 대 혼합 비행단은 실제 0.02인데 경량 판정은 0.93이다.
- 원인: 함종 상성을 단일 전력값의 합으로는 표현할 수 없다.
- 지시대로 기존 함선 전체의 NPC 전투 규칙은 바꾸지 않았다.
- 확인 방법:
  - 월드 NPC 경량 판정 해시(`light-digest.ts`, 표준 월드 시드 11/23/71 × 6 h)가 `15de811`과 같다: `d76e7160d3b2`, `324611f607e7`, `10bec499997c`.
  - 개발 공개 모드에서도 NPC는 항모가 없다. 따라서 경량 판정에 항모가 들어가는 경우는 플레이어 항모가 NPC 전투에 휘말릴 때뿐이다.

## 8. 정식 공개 판단과 운영 배포 절차

**판단:** 개발 환경에서 항모의 전체 생애 주기(획득 → 운용 → 손실 → 인양 → 저장·복원 → 관전·리플레이)가 실제 서버·실제 DB 경로로 동작했다. 기존 저장본·기존 전투 기록의 호환성도 확인했다. 코드 측면에서는 공개할 수 있다. 다만 다음은 이번 작업에서 하지 않았고, 승인이 필요하다.

1. **운영 공개 코드 변경 (별도 승인 커밋)**
   - `carrierRelease.ts`의 운영 조건을 바꾸는 작은 변경이다. 예: 운영 공개 플래그 추가, 또는 기본값 공개.
   - 서버와 클라이언트를 같이 바꿔야 한다(`BATTLE_RULES`와 `hullReleased`/`gearReleased`는 양쪽이 같아야 한다).
   - 이 변경에 맞춰 공개 게이트 시험(`tests/p166-dev-release.test.ts`의 운영 기본값 시험)의 기대값을 갱신한다.
2. **배포 전 백업**
   - 운영 DB를 `pg_dump`로 백업한다(`siderarium_world`, `siderarium_accounts`, `siderarium_sessions`).
   - 백업 파일의 sha256을 기록한다.
3. **운영 사본 사전 검증**
   - 백업을 로컬 임시 DB 또는 JSON 사본으로 풀어서 `mig-verify.ts`를 실행한다.
   - 확인할 것: 멱등, 차이는 시장 10행 + `carrierV`, 전투 기록 재생 동일, 롤백 동작.
4. **배포**
   - 새 코드를 배포하고 `CARRIERS_P16_MIGRATE=1`로 한 번 시작한다.
   - 로그에서 "P16 항모 … 적용 — 시장 10행"을 확인한다.
   - 재시작 시 "건너뜀 — 이미 적용됨"이 나오는지 확인하고, 이후 플래그를 제거한다.
5. **공개 후 확인**
   - 새 전투가 규칙 3인지 본다.
   - helios·bastion에 항모 장비 시장이 있는지 본다.
   - 기존 전투 기록의 리플레이가 정상인지 본다.
   - 모니터링으로 서버 틱 시간을 본다.
6. **롤백**
   - 코드만 되돌리는 경우: 구 서버는 마이그레이션된 저장본에서도 정상 동작한다(§3). 항모 시장 행은 남지만 판매되지 않는다.
   - 데이터까지 되돌리는 경우: 2단계 백업을 복원한다. 복원된 원본에서 구 서버 동작을 검증했다.
   - 공개 이후 플레이어가 만든 항모·장비가 있다면, 데이터 복원은 그 진행을 잃는다. 롤백 방식은 공개 이후 경과 시간에 따라 결정해야 한다.
