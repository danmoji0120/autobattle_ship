# P9.6.2 정거장 코어 설립 비용

## 기준과 범위

- 기준 커밋 `161fd0688134bcf9da95c1f4f99c4f2a7cdffadc`, 작업 브랜치 `codex/p962-core-economy`.
- 성장 월드에서 새로 발행하는 S/M/L/XL 설립 명령에 다음 비용을 적용한다. 시설별 비용·운영비·전력·용량·정박·생산 규칙과 c0 비용은 바꾸지 않는다.

| 규모 | 선납 설립비 | 코어 건설 자재 |
| --- | ---: | --- |
| S | 16,000 cr | 합금 600 |
| M | 60,000 cr | 합금 1,800, 구조재 60 |
| L | 250,000 cr | 합금 7,000, 구조재 400, 기계부품 150 |
| XL | 1,200,000 cr | 합금 30,000, 구조재 2,000, 기계부품 800, 전자부품 300 |

기본 공작선의 화물칸은 300이므로 S급도 추가 운송 또는 왕복이 필요하다. 구매한 물품은 구입 장소에 남고, 현장에 실제 반입된 자재만 예약·소비한다. 코어 비용은 설립 명령에서 한 번 선납하며 시설 등록 비용을 추가 청구하지 않는다.

## 저장 호환성

이미 만들어진 코어 건설 계획은 저장된 `materials`, `paid`, `reserved`, `used`를 그대로 사용한다. 규모 없는 과거 계획은 기존 코어 정의를 유지한다. P9.6의 공작선이 아직 부지에 도착하지 않은 경우에는 저장된 규모와 선납액으로 당시 자재 조건을 복원한다. 같은 규모로 명령을 다시 지정해도 이전 선납액과 조건을 유지하며, 규모를 바꾸면 새 규모의 비용과 기존 선납액의 차이만 정산한다. 중단 시 실제 선납액만 한 번 환급한다.

새 성장 월드 설립 명령에는 서버가 정한 선택 필드 `foundationMats`를 저장한다. 클라이언트가 보내는 값은 사용하지 않는다. 신규 명령의 조건을 출발 시 고정하고 부지 도착 후 기존 `Module.materials`로 전달한다. 저장·콘텐츠 버전과 기존 저장 자산은 변경하지 않는다. 이전 조건 판별은 이 단계의 P9.6 규모별 선납액을 이용하므로, 향후 가격을 다시 변경해 기존 선납액을 재사용할 때는 이 호환 규칙도 함께 검토해야 한다.

이전 버전의 서버는 새 `foundationMats`를 사용하지 않으므로, 새 비용으로 출발한 명령이 남은 저장을 이전 바이너리로 롤백하는 것은 검증·보장하지 않는다. 이번 작업은 운영 서버에 적용하거나 저장을 마이그레이션하지 않았다.

## 검증

- `tests/p962-core-economy.test.ts`: 네 규모의 독립적인 명시 가격·자재 값, 선납, 현장 부분 반입과 대기, 예약·선납금 재시작, 나머지 반입과 실제 소비·완공을 검사했다. 네 규모의 이전 저장 명령, 같은 규모 재지정, 구형 명령의 임의 자재 필드, 규모별 차액과 환급, 기존 예약 중 계획도 확인했다.
- P9.5·P9.6 건설 물류 및 산업 흐름과 함께 표적 검사 54개 통과. 시장 구매품 600을 두 화물선으로 여러 게이트를 거쳐 운송하고, 운송 중 복원한 뒤 정확히 한 번 소비하는 경로를 확인했다. S급 산업 흐름도 공작선과 별도 화물선의 실제 구매·운송으로 완공한 뒤 채굴·정제·출하까지 통과했다. `artifacts/p962/targeted.txt`.
- 다른 기존 시험의 정거장 픽스처에 별도 수송선과 실제 시장 구매를 추가했다. 자금이 부족해진 60,000 cr 픽스처 둘과 XL을 감당하지 못하는 1,000,000 cr 픽스처는 시험 자금만 올렸다. 관련 선택 회귀 11개 통과 (`artifacts/p962/fixture-target.txt`). 개발 중 한 픽스처의 자금 부족과 신규 검사의 운송선 운영비 누락이 발견되어, 실제 설립비·운영비를 구분하도록 고친 뒤 재시험했다.
- 브라우저: 로컬 격리 월드에서 네 규모의 설립비·자재, XL 선납과 자재 부족을 확인했다. XL 현장에 합금 3,000을 실은 시험 수송선이 실제 반입했을 때 예약 3,000과 부족 27,000으로 바뀌고 건설은 대기했다. Chromium 검사 14개 통과, 브라우저 오류 0. [설립 화면](../artifacts/p962/xl-founding-1440.png), [XL 부족량](../artifacts/p962/xl-shortage-1440.png), [모바일](../artifacts/p962/xl-shortage-390.png). 재현: 로컬 전용 Vite를 `127.0.0.1:5177`에 실행하고, 별도 설치된 Playwright·Chromium으로 `node scripts/p962-browser.cjs`를 실행한다.
- P9.5·P9.6의 수동 브라우저와 멀티플레이 재현 스크립트에도 과거 가격이 고정되어 있어 픽스처를 갱신했다. 이전 산출물을 덮어쓰지 않도록 `SIDERARIUM_ARTIFACT_DIR`을 지정할 수 있다. 새 600개 자재를 UI에서 구매·다중 게이트 운송·복원·완공하는 브라우저 검사는 각각 17개와 32개 통과했다. 격리된 두 계정과 파일 저장 서버의 멀티플레이 검사는 각각 16개와 22개 통과했으며, 자재 300만 도착했을 때 코어가 대기하고 재고가 보존되는 것도 확인했다. 로그: `artifacts/p962/p95-browser.txt`, `p96-browser.txt`, `p95-multiplayer.txt`, `p96-multiplayer.txt`.
- PostgreSQL: 별도의 루프백 전용 일회용 컨테이너에서 서버 프로세스를 재시작해 7개 통과. 신규 코어 자재·예약·선납금과 진행 중인 이전 XL 명령의 이전 비용·자재 조건도 확인했다. 사용한 컨테이너는 삭제했다. `artifacts/p962/postgres.txt`.
- c0: 지정 기준 커밋과 고정 시드 5성계·두 회사에서 1,800게임초를 비교해 분당 상태 해시 30/30 일치, 경제 분석 잔차 0. `artifacts/p962/c0-results.json`.
- 빌드와 콘텐츠 검증: 통과, 콘텐츠 오류·경고 각각 0건.
- 최종 전체 회귀: 기존 시간 제한을 유지하고 `env -u PG_TEST_URL npx vitest run --maxWorkers=1 --reporter=verbose`를 처음부터 실행해 **304개 통과, 7개 건너뜀, 실패 0개** (38개 파일 중 37개 통과, PostgreSQL 전용 1개 건너뜀). PostgreSQL 7개는 위의 격리 실행에서 모두 통과했다. `artifacts/p962/full-regression.txt`에 기록했다. 앞선 실행은 위의 오래된 수동 검증 픽스처를 발견해 완료 전에 중단했고 (`artifacts/p962/interrupted-regression.txt`), 스크립트 수정·재검증 후 최종 전체 회귀를 다시 시작했다.

전체 회귀 외에 운영 DB, 운영 서버, 실제 운영 저장이나 통합 브랜치는 사용하거나 변경하지 않았다.
