# P9.6.3.1 조선 등급과 건설 자재 안전성

## 범위와 기준

기준은 `codex/p963-facility-economy`의 `793ff7746ae08c2500d4c4c44eb39aed99ed9b22`, 작업은 `codex/p9631-yard-cargo-safety`에서 수행한다. 운영 서버·DB·월드와 통합 브랜치는 변경하지 않는다. P9.6.2의 코어 조건과 P9.6.3의 43개 시설 비용·재료·최소 규모, 전력·설치 용량·작업 시간은 유지한다.

## 조선소와 연구

| 선체 | 이전 | 신규 |
| --- | ---: | ---: |
| `battleship_mk1` 아퀼라급 | 3 | 4 |

소형 독은 초계함·호위함·소형 산업선, 중형은 구축함·경순양함·중형 산업선, 대형은 중순양함·순양전함·대형 산업선, 초대형은 전함·드레드노트·초대형 산업선을 건조한다. 상위 독은 하위 등급도 건조한다. 물리적 선체 크기·정박 등급은 별개다. 공유 `HULLS.battleship`을 바꾸면 c0 규칙과 공영 판매 재고가 달라지므로 성장 월드의 `battleship_mk1` 건조 요구에만 4를 적용한다. 다른 클래스의 공통 등급은 변경하지 않는다.

성장 월드의 초대형 독 시설은 기존 대형 독 선행 조건과 함께 `capital_hulls`를 요구한다. 전함은 기존 전함 설계 연구와 설계도, 드레드노트는 `dreadnought_program`과 전용 설계도, 초대형 산업선은 각각의 기존 연구와 설계도를 별도로 요구한다. 독 자체에 드레드노트 연구를 요구하지 않는다. c0 월드는 구형 조건인 `dreadnought_program`을 유지하며 시설·연구 설명과 완료 알림도 해당 월드의 규칙을 따른다. `TIER_BASE`는 그대로이며 새 등급의 산업시설 조건이 적용된다. 완성 함선의 공영·플레이어 거래는 직접 건조 권리와 별개다.

기존 구현은 조선 등급을 건조 요금·NPC 가격·재고 산정에도 사용했다. 등급만 수정하면 명시적으로 유지해야 하는 가격과 판매 정책이 바뀐다. 따라서 8개 선체의 이전 등급을 **가격 산정 기준**으로 따로 유지하고, 실제 건조 가능 독과 필요 산업시설에 새 등급을 적용한다. `scripts/p9631-baseline-check.mjs`는 32개 선체의 건조 공임·부품·시간, 판매 가격·재고·보충 재료, 운항 성능·유지비, 변형·프리셋과 시설·연구 데이터를 기준 커밋과 비교한다.

새 성장 월드 건조 계획에는 `requiredYard`를 저장한다. 필드가 없는 과거 계획의 8개 선체는 위 표의 이전 등급을 사용하고 그 등급의 `TIER_BASE`를 적용한다. 이미 착공한 계획과 부품을 기다리는 계획을 모두 보존하며 재청구하지 않는다. 다른 구형 계획은 종전 계산을 사용하고, c0 새 계획에는 이 필드를 추가하지 않는다. 선택적 필드 외의 저장 마이그레이션이나 콘텐츠 버전 변경은 없다.

## 창고 초과와 입고

건설 취소는 기존대로 미사용 예약 자재와 선납금의 미진행분을 정확히 한 번 반환한다. 반환 후 보관량이 용량을 넘더라도 자산은 회사별 기존 창고에 남는다. 초과량은 저장된 별도 무한 창고가 아니라 `max(0, 실제 재고 − 용량)`으로 계산하며, 일반 입고는 공간이 생길 때까지 차단한다. 출고·판매·자재 소비와 창고 증설은 가능하다.

예약과 취소를 반복해 입고 한도를 무제한 우회하지 못하도록, **성장 월드 자사 정거장의 일반 입고 여유**는 실제 창고 재고에 반환 가능한 건설 예약과 해당 회사의 판매 매물도 더해 계산한다. 공용 창고도 해당 회사의 매물 반환 공간을 고려한다. 예약·매물은 여전히 별도의 기존 자산이며 창고 수량에 중복 표시하거나 소비하지 않는다. 매물 회수와 건설 취소는 그대로 허용한다. 다른 회사의 매물은 자기 회사의 여유 공간에 합산하지 않는다. 저장 공간이 모자라면 대기 중인 수송선에 화물과 노선 명세가 남는다.

대량 독을 순차 공급할 수 있도록 **건설 목적 반입**은 실제 빈 창고 공간에서 해당 계획의 부족 재료에 한해 허용한다. 창고가 이미 물리적으로 꽉 차거나 초과하면 건설 목적 반입도 막는다. 소유자가 판매 매물에 숨긴 같은 자재는 건설 공급 부족분에서 제외해 매물 회수와 반복 공급으로 초과분을 계속 늘리는 우회도 막는다. 그런 자재는 매물을 회수한 뒤 건설에 쓸 수 있으며 건설 화면에 이유가 표시된다. 무규모 성장 정거장도 예약·매물 반환 보호를 적용하지만 과거 용량과 시설 설치 조건은 그대로다. c0에는 적용하지 않는다.

초과 중에도 재고량을 줄이는 생산 배치는 원료를 소비할 수 있다. 완성품이 실제 용량을 넘으면 기존 생산 작업 안에 보존되고 공간이 생길 때 한 번만 입고된다. 시설 철거는 회수 자재와 예약·매물 반환분을 보관할 공간이 없으면 거부한다. 원격/자사 시장 구매, 수동 하역, 자동 물류 및 피팅 해제도 여유 공간을 검사한다. 취소 알림·창고·건설 화면은 초과량과 해결 방법을 표시한다.

## 검증 범위

- 19개 선체를 S/M/L/XL 독에 실제 서버 건조 명령으로 등록해 허용·거부, 선납 및 거부 시 무차감을 확인했다. 연구·설계도·시설을 분리해 검사했으며 완성 함선의 NPC 구매도 권리 없이 실행했다. 시험 자금과 설계도·연구·시설은 지급했다.
- 구형 대형 독 전함, 중형 독 대형 채굴선, 대형 독 초대형 채굴선의 각각 진행 중·미착공 계획을 저장·복원하고 실제 서버 건조 로직으로 두 척을 각각 한 번 진수했다. 새 드레드노트와 XL 수송선도 실제 부품 소비와 진수까지 검사했다. 이 완료 검사는 남은 게임 시간을 큰 전략 틱으로 가속했으므로 장시간 실시간 운영 시험은 아니다.
- XL 독 재료 81,850을 예약·취소해 1,850 초과 상태와 정확한 환급을 확인했다. 재취소·다른 회사 명령 거부, 재등록·재예약, 수동 하역·시장 구매·피팅·창고 철거 차단, 판매 매물 우회 차단, 생산 원료 소비와 완성품 대기, 운송 중 화물·노선 저장 복원, 실제 반출 후 자동 입고 재개를 검사했다. P9.6.3의 XL 다회차 공급과 독 완공 검사도 유지한다.
- 기준 c0 5성계 월드에서 정제소·소형 독과 대형 독 전함 계획을 실행하고 1,800초 동안 매 분 상태 해시 30개를 비교했다. 별도 복제 월드에서 초대형 독의 기존 연구 조건에 따른 거부와 허용도 기준 커밋과 비교했다. 결과는 `artifacts/p9631/c0-results.json`이다.
- 격리 브라우저는 시험 정거장과 자금·연구·설계도를 지급하고, 대형 독의 전함 건조 거부를 실제 명령과 화면에서 비교했다. 서버에서 XL 독 예약·취소를 실행해 초과 경고를 확인했다. ## 검증 기록과 제한

- 최종 코드의 단일 워커 전체 회귀: **338개 통과, 0개 실패, 8개 건너뜀** (42개 테스트 파일 통과, 약 948초). 건너뛴 8개는 PostgreSQL 전용이며 아래 별도 격리 실행에서 모두 통과했다. `artifacts/p9631/full-regression.txt`.
- 기준 커밋과 시설 44행(코어 포함), 선체 32종, 모든 선체 변형·프리셋과 NPC 공급·가격을 비교했다. 콘텐츠 검사 오류·경고 0, 타입 검사와 빌드 통과. `artifacts/p9631/baseline-comparison.json`, `content-final.txt`, `build-final.txt`.
- 관련 조선·물류·창고·경제·P8 및 소유권 검사 104개 통과, 추가 신규 집중 검사 19개 통과. 기존 P9.6.3 L/XL 다회 운송과 S/M 산업 흐름 4개도 통과했다. c0 조건 수정 후 조선·창고·연구 표적 검사 **29개**가 다시 통과했다. `artifacts/p9631/target-final2.txt`, `target-logistics-final.txt`, `target-c0-fix.txt`.
- 최종 코드의 브라우저에서 실제 건조 명령 오류, 초대형 독 연구 조건, 서버 취소 후 초과량, 1440px와 모바일 390px을 포함해 **9개** 확인 항목 통과, 런타임 오류 0. `artifacts/p9631/browser-final.txt`.
- 최종 빌드로 루프백 전용 일회용 PostgreSQL에서 서버를 두 차례 재시작해 예전 전함 계획의 3등급과 새 계획의 저장 등급, 초과 재고를 검사했다. 기존 검사 포함 **8개 모두 통과**. 컨테이너는 종료 후 삭제했다. `artifacts/p9631/postgres-final3.txt`.
- 개발 중 첫 PostgreSQL 실행에서 새 픽스처가 기존 대형 채굴선의 하역시설 요구를 빠뜨려 1개 실패했다. 픽스처에 하역시설을 추가한 뒤 8개가 통과했다 (`postgres-initial.txt`, `postgres-retest.txt`). 최종 재실행 한 차례는 기존 준비 스크립트가 출력 없이 종료돼 원인을 확정하지 못했다. 준비 단계 진단을 명시한 동일 격리 방식의 `scripts/p9631-postgres-check.sh`로 다시 실행해 8개가 통과했다. 테스트 시간 제한은 변경하지 않았다.
- 관련 회귀 초기 실행에서 기존 경제 테스트 1개는 조선 등급과 NPC 판매 기준을 동일하게 가정해 실패했다. 요구된 기존 판매 정책을 유지하도록 경제 기준을 확인하는 테스트로 수정했다. 같은 실행의 다른 2개는 실행 중 파일을 편집해 서로 다른 코드 버전이 섞였고, 코드가 안정된 뒤 관련 104개와 신규 검사를 재실행해 통과했다 (`target-systems.txt`, `target-final2.txt`).
- 전체 회귀 진행 중 최종 검토에서 초대형 독 연구 조건이 c0에도 적용되는 호환성 문제를 발견해 검사를 중단했다 (`full-interrupted-c0-fix.txt`). 성장 월드와 c0의 조건·표시를 분리하고 표적 검증과 최종 전체 회귀를 다시 수행했다.

**기존 별도 제한:** 기준 커밋과 현재 코드 모두 타사 사설 정거장의 거래시설에서 물품을 구매하면 구매자별 보관함에 물품은 기록되지만, 구매자는 해당 정거장에 정박할 수 없어 수송선으로 직접 회수할 수 없다. 실제 시뮬레이션과 기준 비교를 `baseline-comparison.json`에 기록했다. 자산의 소유권은 분리되며 완성 함선은 별도 거래 경로에서 구매 후 출항할 수 있음을 검사했다. 정박·거래 권한 정책의 재설계는 이번 범위를 벗어나 미해결로 둔다.

**검증 한계:** 시험에서 자금·설계도·연구·시설과 원료를 지급했으며, 초대형 선박의 완료는 시간을 가속한 서버 전략 틱으로 검사했다. 장기간 실시간 다중 사용자 경제·전투 부하는 검증하지 않았다.
