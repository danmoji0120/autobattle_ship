# P9.6.3.2 거래·화물 인수 검증

기준은 원격 `codex/dev11-combat-lab-ui`의 `1ffbcebb4df473159deccd50d92c92caa1fcf48d`이다. 운영 월드, 운영 DB, 통합 브랜치는 사용하지 않았다. 실험 세계의 자금·물자는 명시적인 테스트 픽스처이며 실제 플레이의 획득량을 뜻하지 않는다.

## 확인된 문제와 수정

- 성장 월드에서 응답이 유실된 판매·매물 등록·매물 구매·매물 회수 요청은 재전송 시 재고나 대금을 다시 처리했다. NPC 조선소의 함선 구매도 남은 재고가 있으면 같은 요청으로 또 구매했다. 거래가 끝난 중고 함선 구매는 재전송 시 실패 응답을 줬다. `Company.lastTrade`에 마지막으로 성공한 순번·식별자·명령 서명을 저장하고, 클라이언트의 미확인 요청은 기존 구매 요청과 같은 방식으로 재사용한다. 동일 요청의 재전송은 성공을 재확인하고, 다른 명령에 식별자를 재사용하거나 과거 순번을 보내면 거부한다. 정상 확인 후 새로 실행한 거래는 새 순번을 사용한다. 기존 NPC 상품 구매의 `lastPurchase`는 그대로 유지한다.
- 거래소 등록에서 자사 창고의 실제 속성이 아닌 JavaScript 상속 속성(`__proto__` 등)을 품목으로 보내면 보유하지 않은 매물을 만들 수 있었다. 창고 자체의 유한한 실제 재고인지 확인하고 상속 속성 이름을 거부한다. 잘못된 품목·수량의 상품 매물은 거래와 회수를 거부하고 기록을 보존한다. 가격이 음수이거나 유한하지 않은 함선 매물, 판매 회사가 없는 상품·함선 매물도 결제 전에 거부한다.
- 타사 사설 거래소에서 정상 구매한 물자는 구매자의 해당 정거장 보관함에 들어가지만 정박 권한이 없어 회수할 수 없었다. 기존 관리형 물류가 구매 회사의 재고만 외부 접근해 적재하도록 연결했다. 타사 창고 열람·정박·목적지 입고 권한은 부여하지 않는다. 기존 노선은 출발 재고가 일시적으로 0이어도 재개하여 다음 물자를 기다릴 수 있다. 함선이 실제 이동하고 기존 화물 처리 시간·명세서·용량·하역 규칙을 따른다.
- 중고 함선은 화물 0.5 이하를 빈 화물칸으로 간주해 판매할 수 있었고, 남은 소량 화물도 구매자에게 넘어갔다. 이제 소량 화물이 있는 함선의 신규 매물 등록과 구형 매물 구매를 거부하며, 판매자는 매물을 내리고 하역할 수 있다. 함선 거래·상세와 창고 화면도 0.5 미만 재고를 숨기지 않는다.
- 기존 비관리형 운송은 0.5 이하의 선적 화물이 있으면 빈 배로 판정하면서 적재 가능량 계산에서 그 화물을 빼지 않아, 450 용량에 450.25를 실을 수 있었다. 남은 실제 공간만 적재하게 수정했다. 이 안전 수정은 c0에도 적용되므로 해당 오류 사례의 c0 동작은 의도적으로 달라진다. 정상 거래 시나리오의 c0 비교 결과와 이 예외를 각각 기록한다.
- 설계도 조각 `bpf:`의 실제 저장 키가 관리형 운송의 품목 검사에서 빠져 있었다. 기존 물류 경로로 운송할 수 있게 했다.
- 물류 화면의 화물 한도는 자동 운송에 적용되는 연구 배율을 표시하지 않았고, 수동 하역 명령을 접수할 때 즉시 하역이 끝난 것처럼 안내했다. 운송에 실제 적용되는 한도를 표시하고 비동기 처리 중인 화물이 함선에 남아 있음을 안내한다.

기존 NPC 시장의 가격·세금·예산 및 부분 체결 정책은 유지한다. 재고가 0이거나 자금이 부족하면 거래를 거부하고, 일부 재고 또는 매입 예산만 있으면 가능한 수량만 거래한다. 공공 창고·화물칸 구매는 요청 수량이 남은 용량을 넘으면 결제하지 않는다. 창고가 찬 목적지에서는 미인수 화물을 함선에 유지한다.

## 저장 및 호환성

`lastTrade`는 선택적인 회사 JSON 필드다. 기존 저장에 없어도 새 거래부터 기록되며, 별도 DB 스키마 변경·콘텐츠 마이그레이션은 없다. 회사별 스냅샷에는 자기 회사의 기록과 창고만 표시한다. 기존 정거장·시설 비용, P9.6.3.1 조선소 등급, 가격과 생산량은 변경하지 않았다.

호환성을 위해 요청 식별자가 없는 구형 클라이언트의 명령도 계속 허용한다. 따라서 **식별자 없는 요청은 의도적인 재구매와 재전송을 구별할 수 없어 중복 실행을 보장해서 막을 수 없다.** c0 거래 명령에는 새로운 재전송 보호를 적용하지 않는다. 확인된 새 클라이언트의 보호 대상은 NPC 상품 구매·판매, 상품 매물 등록·회수·구매, NPC 함선 구매와 중고 함선 구매다. 서버에는 최신 성공 요청 한 건만 보관하므로 더 오래된 요청은 안전하게 거부되지만 이전 성공 결과를 다시 알려 주지는 않는다.

미확인 요청의 클라이언트 기록은 기존 구현과 같은 `sessionStorage`에 있으므로 같은 탭의 새로고침과 서버 재시작을 복구하지만, 탭을 닫거나 브라우저가 해당 저장소를 보존하지 않으면 재전송 식별자를 복구한다고 보장할 수 없다. 저장이 끝나기 전에 서버가 강제 종료되는 경우도 별도로 남는다. 기존 서버는 성공 응답과 DB 저장을 한 트랜잭션으로 묶지 않고 기본 30초 간격으로 비동기 스냅샷을 저장한다. 따라서 마지막 성공 응답 뒤 아직 저장되지 않은 상태는 비정상 종료 후 되돌아갈 수 있다. 저장된 스냅샷의 자산·식별자는 함께 복원되는 것을 검증했으며, 모든 성공 거래의 즉시 내구성을 보장하려면 별도의 원자적 영속화 설계가 필요하다.

기존 연구 화물 배율은 자동 운송과 공작선 건설 자재에 적용되나 직접 구매·채굴의 화물 제한에는 적용되지 않는다. 이 불일치는 이전 코드에도 있으며, 이번 작업에서 함선 적재량과 경제 규칙을 바꾸지 않았다. 물류 화면은 자동 운송 경로에 실제 적용되는 값을 표시한다. 전반적인 화물 한도 통일은 별도 설계·회귀 검토가 필요하다.

## 재현 및 브라우저

수정 전 실패 기록은 `artifacts/p9632/repro*before.txt`에 남겼다. 정상 거래 외에도 두 회사의 격리, 자금·재고·창고·선창 부족, 부분 하역, 중복 요청, 실패한 매물, 재시작과 연속 운송을 표적 검사했다. 거래소 세금과 NPC 시장의 재고·예산 변동은 기존 정책을 따른다.

`node scripts/p9632-trade-browser.mjs`는 임시 싱글플레이 저장만 사용한다. 구매 버튼을 두 번 입력했을 때 구매자 -10 cr, 판매자 +9.5 cr, 사설 거래소 재고 +1로 1회 처리됐고, 실제 운송 후 목적지 +1·출발지 0·함선 화물 0을 확인했다. 브라우저 저장·재시작 이후에도 결과가 유지됐고 오류는 없었다. 자동 검사의 첫 시도는 확인 대화상자를 수락하지 않아 시간 초과됐으며, 하네스를 수정한 뒤 재검증했다. 데스크톱과 모바일 화면: `artifacts/p9632/fractional-ship-1440.png`, `artifacts/p9632/fractional-warehouse-1440.png`, `artifacts/p9632/market-1440.png`, `artifacts/p9632/pickup-route-1440.png`, `artifacts/p9632/pickup-route-390.png`.
