# P9.6 정거장·시설 체계

## 범위와 기준

- 기준: `codex/p95-construction-logistics`, `cfc3717912a5da563eabe593d325ce77a3062035`.
- 별도 작업 브랜치: `codex/p96-station-facilities`. 운영 서버·운영 DB·기존 월드에는 적용하지 않는다.
- 기존 시설 정의, 건설 예약, 공작선, 채굴, 생산, 조선, 연구, 정비, P9.5 물류를 재사용한다. 정거장·시설 설계도는 추가하지 않는다. 함선·무장·부품의 기존 설계도와 연구 조건은 유지한다.

## 규모와 설계 근거

건설 비용은 코어 설립 시 선납하며, 자재는 건설 현장에 실제로 들어와야 한다. 작업량은 코어 건설의 기존 시간 단위다. S는 P9.5의 8,000 cr/합금 300 진입 비용을 유지한다. 대신 S는 저렴한 운영비와 접근성을 얻고, 창고·처리량·정박·산업 규모에는 명확한 제약을 둔다. 다른 크기는 자본과 매시간 비용을 더 내고 거점을 확장한다. 기존 함선과 시설의 가격, 생산량, 연구 시간이나 전역 시장 가격은 변경하지 않았다.

| L | 50,000 cr | 합금 1,400, 구조재 80, 기계부품 30 | 180 | 80 | 24 | 30,000 | L 이하 14척 | 3 | 35 | 800 cr |

운영비는 코어가 완공된 뒤 기존 함대 운영비 계정에 누적·정산되며, 체납 역시 기존 규칙을 따른다. 비교 기준인 기존 기본 채굴선·수송선·공작선의 운영비는 각각 대략 350/300/600 cr/시간이다. S 코어는 이보다 낮지만 무한한 시설과 무료 확장을 제공하지 않는다.

코어는 시설 용량을 차지하지 않으며 일반 시설과 예정 계획은 각각 1, 조선소는 규모 단계에 따라 1~4를 차지한다. 같은 계획도 즉시 용량을 예약하므로 동시에 발주해 한도를 넘길 수 없다. 기존 40개 물리 슬롯 한도도 적용된다. 상위 조선소와 일부 고급 공장은 규모의 산업 단계와 기존 연구·선행 시설을 모두 확인한다. 창고 시설은 기존대로 하나당 30,000을 더한다. 하역시설과 격납시설은 정박 정원을 각각 2척 더하고, 정원은 기존 배치 좌표의 최대 28척을 넘지 않는다. 하역시설은 기본 화물 처리율을 개당 50% 더한다. 속도는 정박 작업 중인 **각 함선** 기준이며 동시에 이용하는 함선 수는 정박 정원으로 제한된다.

## 시설과 서버 규칙

- 기반: 코어, 발전소, 창고, 하역시설, 거주 시설. 코어 완공 전 현장은 일반 창고가 아니지만 남은 건설 자재를 필요한 수량만큼 받을 수 있어 첫 시설 설치가 막히지 않는다.
- 산업: 기존 정제소와 금속·합금·기계·구조재·전자부품 등 생산 시설. 창고의 현장 재고만 입력으로 사용하고 완료된 생산물도 현장 창고에 들어간다.
- 조선과 연구: 기존 조선소 단계·건조 슬롯·연구실 및 함선별 설계도 검사를 그대로 사용한다. 건조가 끝나도 정박 정원이 가득 차면 완성된 선체를 대기열에 보존한다.
- 수리·보급과 지원: 기존 수리시설·격납시설·군수창고·방어시설·피팅·물류센터·거래시설을 연결한다. 완공 시설은 각 자재의 50%를 소수점 이하는 버려 회수하며 크레딧은 환급하지 않는다. 건설 당시 자재를 기록한 신규 시설은 그 기록으로 회수량을 계산하고, 과거 시설은 기존 정의를 사용한다. 진행 중인 작업, 의존 시설, 거래 매물, 정박 정원, 회수 후 창고 용량을 검사해 안전하게 철거할 수 없으면 보류한다.

완공 시설의 전력 생산과 소비를 합산한다. 규모형 정거장의 생산·조선·연구와 화물 처리·자동 정비는 공급/수요 비율에 따라 느려진다. 즉시 실행해야 하는 피팅·수동 수리·거래와 군수창고·방어 지원은 전력이 완전히 충족될 때만 가동한다. 건설 중인 시설은 전력과 기능을 제공하지 않는다. 창고와 물리 정박 공간은 정전 때도 유지해 기존 자산이나 함선이 사라지지 않는다. 생산 중 창고가 차면 완성 배치는 작업 상태로 보관하고 공간이 생길 때 한 번만 입고한다.

## 구매·운송·건설

성장 월드의 신규 설립 명령은 규모를 명시하며 구형 클라이언트가 생략하면 S를 선택한다. 크레딧 선납 상태는 기존 P9.5 방식으로 저장되고 명령 중단 시 환급된다. 다른 규모로 목적지를 다시 지정하면 선납 차액만 정산한다. 공작선에 적재된 자재와 정박 중인 바로 그 정거장의 자사 재고만 공작선에 실을 수 있다. 다른 시장에서 구매한 물품은 판매처의 자사 보관함 또는 정박한 자사 화물칸에 남는다.

기존 건설 계획은 현장 입고분만 예약하고, 기존 반복 운송 또는 직접 반입으로 부족분을 공급한다. 완공된 규모형 정거장의 적재·하역은 전력과 처리율에 따라 시간이 걸린다. 처리 중 적재 재고는 출발지에, 하역 화물은 함선에 남는다. 처리가 끝나는 시점에 다시 실제 수량·공간·권한을 확인하고 한 번만 이동한다. 명령 변경·중단·목적지 상실·창고 포화 시 물품을 버리지 않는다. 초기 코어 미완성 현장에는 기존 P9.5의 제한된 직접 건설 반입을 적용한다.

## 저장과 호환성

저장 형식에 선택 필드 `Station.size`, `Module.materials`, `Module.work`, `WShip.cargoWork`, 설립 명령의 `size`를 추가했다. 자재·진척·처리 중 물품의 소유 위치는 기존 창고·화물·예약에 남으며 별도 자원 복사본을 만들지 않는다. 하역 작업은 직렬화되어 재시작 후 이어진다. 다른 회사의 스냅샷에서는 화물 처리 세부 정보를 숨긴다.

규모가 없는 기존 정거장과 저장된 진행 중 과거 설립 명령은 기존 용량·전력·시설·정박·운영비 규칙을 유지한다. 자산을 축소하거나 일괄 변환하지 않는다. c0에서는 신규 규모 명령과 시설 철거가 적용되지 않는다. 과거 저장을 자동으로 새 규모로 재작성하거나 P9의 22성계·게이트·콘텐츠 버전을 변경하지 않는다.

## 검증 결과

검증은 로컬 개발 월드와 폐기 가능한 데이터베이스에서 수행했다.

- 규모별 코어 비용·자재·전력·시설 한도·정박 및 산업 제한, 선납 차액과 환급, 전력 제한·복구, 저장 공간 부족, 운영비 정산, 철거·회수, 선체 출고 대기, 하역 중 재시작: `tests/p96-stations.test.ts`.
- `tests/p96-industrial-flow.test.ts`: 앤빌 광구에서 공작선이 S 코어를 완공하고, 아스트라·포지·하버에서 **실제 구매한** 자재를 여러 게이트를 건너 운송해 창고·하역시설·정제소를 설치한다. 기존 채굴선의 광석을 정제한 뒤 금속을 아스트라로 운송했다. 최초 함선과 시험 자금은 격리 픽스처이며 시장 구매·설립·이동·시설 건설·채굴·생산·운송은 게임 명령과 틱을 사용한다. NPC 위협은 시험의 재현성을 위해 비활성화했다.
- 표적 시험: P9.6 19개 통과. 기존 연구 조건과 P8 다섯 함선 설계도·제조 시험을 포함한 선택 회귀도 통과했다. 구형 조선소의 자산을 검증하는 P8 픽스처는 명시적으로 규모 없는 과거 정거장으로 구성했다. P9.5 포화 창고 시험의 고정 20,000은 해당 정거장의 실제 용량을 기준으로 바꿨으며 포화·잔여 화물·재개 검사는 유지했다.
- 최종 `npm run build` 통과. `npm run content:check`는 오류 0건·경고 0건이다.
- PostgreSQL: 로컬 소켓의 Docker 데몬에서 암호가 임의 생성되고 `127.0.0.1`에만 노출되는 일회용 PostgreSQL 컨테이너를 만들었다. 실제 서버 프로세스 재시작 및 구 저장 마이그레이션 경쟁·롤백을 포함한 7개 검사 통과. 신규 S 정거장, 진행 중 생산 및 하역, 자재와 소유권도 두 차례 재시작 후 보존되었다. 컨테이너는 검사 후 삭제했다. `scripts/p96-postgres-check.sh`는 기존 DB 주소를 사용하지 않는다.
- 멀티플레이: 격리된 파일 저장 서버와 실제 두 계정·WebSocket을 사용해 22개 검사 통과. 타사 시설 건설·철거 차단, 재고·하역 정보 비공개, 진행 중 하역·노선·화물·설립 선납금의 프로세스 재시작 복원과 중복 구매 방지를 확인했다. `artifacts/p96/multiplayer-results.json`에 결과를 남겼다.
- c0: 기준 커밋과 동일한 5성계·두 회사·고정 시드 월드를 1,800게임초 동안 나란히 비교했다. 벽시계에 따라 달라지는 기존 NPC 전투 예산은 두 실행에서 같은 값으로 고정했다. 매분 상태 해시 30/30 일치, 최종 SHA-256 `40bb0f711d80a37da3711e2efe53e0512792a3358823953637c411c1657bcec2`, 경제 분석 잔차 0. 실행: `node scripts/p96-c0-check.mjs`.
- 브라우저: 격리 싱글플레이어 Chromium에서 규모 선택, 현장 설립, 시장 구매, 실제 여러 게이트 운송, 리로드, 코어 및 정제소 설치까지 32개 검사 통과, 브라우저 오류 0. 1920×1080, 1440×900, 1024×768, 390×844에서 화면을 확인했고 모바일에서 시설 상세와 건설 명령에 스크롤·접근할 수 있음을 확인했다. 채굴·정제·최종 출하는 위의 서버 시뮬레이션 통합 시험에서 검증했으며 이 전 과정을 브라우저 클릭만으로 반복하지는 않았다.
- 브라우저 재현은 별도 설치된 Playwright와 Chromium이 필요하다. 로컬 전용 Vite를 5175 포트에 실행한 뒤 `node scripts/p96-browser.cjs`를 사용하며, Chromium 실행 경로는 `CHROMIUM_PATH`로 지정할 수 있다. 테스트 자금과 함선은 격리된 브라우저 월드에만 들어간다.
- 전체 회귀: 원래 제한과 단일 워커로 실행한 결과 287개 통과, 3개 실패, 7개 건너뜀이었다. 7개는 별도 격리 PostgreSQL 실행에서 모두 통과했다. 실패 3개는 P5 시험이 S급에 9개 시설을 주입하거나 산업 시험이 4,000 한도의 S 코어에 10,000 또는 4,400의 초기 재고를 직접 넣은 조건 때문이었다. P5는 사전 구성한 M급 시험 기지로, 산업 시험은 동일한 재고량을 수용하는 창고가 있는 S급 기지로 고친 뒤 세 시험을 모두 재실행해 통과했다. 원래 생산량·검증 조건·시간 제한은 유지했으며, 수정은 테스트 픽스처에만 있어 나머지 통과한 테스트를 다시 처음부터 반복하지 않았다. 따라서 단일 실행이 전부 초록색이었다고 주장하지 않는다. 원본과 재시험은 각각 `artifacts/p96/full-regression.txt`, `artifacts/p96/regression-retest.txt`에 남겼다.

기존 `queueModule`은 객체 상속 속성인 `constructor`를 시설 정의로 받아 예외가 발생하면서 회사 크레딧이 비정상 숫자가 될 수 있었다. 지정된 P9.5 기준 커밋에서도 재현해 `artifacts/p96/facility-input-results.json`에 기록했다. 서버가 명령을 수행하기 전에 실제로 정의된 시설 ID인지 확인하도록 고쳤으며, 잘못된 이름은 건설 계획과 크레딧을 변경하지 않는 표적 검사가 통과했다. 이 입력 검사는 c0에도 적용되므로 **잘못된 시설 ID의 오류 처리**는 이전과 달라진다. 정상 c0 명령과 고정 시드 월드의 결정론은 그대로 비교한다. 이 문제를 발견한 시점에 진행 중인 첫 전체 회귀를 중단하고 수정한 뒤 최종 코드에서 다시 실행한다.

## 성능 및 한계

`scripts/p96-performance.mjs`는 기준 커밋, 현재 과거 호환 정거장, 현재 S 정거장을 각각 단일 프로세스에서 순차 실행한다. 각 측정은 준비 80틱 후 0.25초 서버 틱 600회를 재고, 2회 반복한다. 분석을 켜고 클라이언트와 NPC 생성은 끈 합성 건설 공급 부하다.

30개 정거장·30개 노선에서 기준 평균은 틱당 0.986~1.077 ms, S급은 1.014~1.444 ms였다. p95는 각각 2.421~2.438 ms와 2.221~3.605 ms, 직렬화 크기는 188,723과 189,093바이트였다. 각 실행에서 자재 수지 차이는 0이었다. GC 후 힙 변화는 측정 편차가 커 장기 메모리 사용량으로 해석할 수 없다. 이 작은 합성 시험의 편차 때문에 최대 약 46%의 평균 틱 증가가 관찰된 회차도 숨기지 않으며, 다중 플레이어 장기 부하나 실제 운영 서버의 성능을 보장하는 수치는 아니다. 측정 후 비정상 시설 ID 검사 한 줄을 추가했으며, 이 부하에는 시설 등록 명령이 포함되지 않는다. 세부 값은 `artifacts/p96/performance.json`에 있다.

M/L/XL의 비용·예약·시설·정박 제한은 자동 검사했지만 S급과 같은 처음부터 끝까지의 실제 채굴 거점 흐름을 각 규모마다 반복하지는 않았다. 소프트웨어 렌더러에서 브라우저 스크린샷이 한 차례 30초 제한에 걸렸고, 개발 중 코드 갱신으로 한 차례 재접속이 중단되었다. 중복 캡처를 줄인 최종 실행에서 위의 32개 항목이 통과했다. 장시간 집중 회귀에 전체 월드 시험이 중복 포함된 실행은 중단하고 범위를 좁혀 다시 검사했으며, 장시간 검사는 전체 회귀에서 원래 제한 그대로 실행한다.

**P9.6 당시 Partial — 센서·통신시설 설명:** 이 시설은 일부 지휘형 함선 변형의 건조 선행 조건으로 사용되지만, 기존 설명의 위협 탐지 거리 +2,000과 별도 해적 조기 경보는 시뮬레이션에 연결되어 있지 않았다. P9.6에서는 설명이 남아 있었으며, 아래 P9.6.1에서 실제 기능에 맞게 수정했다. 탐지·경보 기능은 구현하지 않았다.

### 범위 밖에서 발견한 기존 설명 차이

다음 항목은 이번 작업에서 기능이나 문구를 변경하지 않았다.

- **지원시설:** 생산 속도 +10%는 적용되지만, 설명의 정박 지휘관 경험 증가 경로는 확인되지 않는다. 지휘관 경험치는 현재 교전 결과에서 증가한다 (`src/world/production.ts`, `src/world/sim.ts`).
- **하역시설:** 설명은 수송선 적재량 증가를 말하지만, 현재 규모형 정거장에는 하역 속도 보너스가 적용되고 적재량은 선체·연구 규칙으로 계산된다 (`src/world/stations.ts`, `src/world/logistics.ts`).
- **수리시설:** 시설 설명의 합금·기계부품 소비와 정거장 화면의 무료 자동 선체 수리 문구는 현재 동작과 다르다. 수동 선체 수리는 크레딧을 쓰며, 자동 정비는 별도의 유료 마모 정비다 (`src/world/sim.ts`, `src/world/upkeep.ts`, `src/client/strategic/hud.ts`).
- **격납시설:** 정박 정원 증가는 적용되지만, 정비 속도 +50%라는 문구와 달리 실제 정비 능력은 시설당 시간당 20포인트가 추가된다 (`src/world/storage.ts`).
- **군수창고:** 설명은 해당 정거장에 정박한 함선을 가리키지만, 실제 탄창 배율은 가동 중인 자사 군수창고가 있으면 회사 함선에 적용된다 (`src/world/sim.ts`, `src/world/industry.ts`).

P9.6에서 남긴 M/L/XL별 전체 채굴 거점 흐름, 브라우저만으로 채굴부터 최종 출하까지 이어지는 흐름, 장기 다중 사용자 부하는 이번 설명 정리에서 재검증하지 않았다. 데스크톱에서 긴 시설 목록의 하단 항목을 선택하면 상세 내용이 목록 위쪽에 나타나 수동 스크롤이 필요할 수 있는 기존 UI도 유지한다.
