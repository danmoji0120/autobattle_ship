# P9.8.0–P9.8.1 자동화 감사 및 공용 물류 검증

기준 `86fa5f7320c3b62a149c7acf116b84d0e1b9dedf`, 작업 브랜치 `codex/p980-p981-autonomous-logistics`. 이 시험은 격리된 개발 월드와 일회용 로컬 PostgreSQL에서 수행했다. 운영 배포·운영 DB 변경·다른 개발 브랜치 병합은 하지 않았다.

**최종 판정: Partial.** 개별 함선 병렬·연속 배차와 실제 자원 예약, 저장 복원 및 장애 복구는 구현하고 아래 범위에서 검증했다. 다만 기존 P9.7 관리형 노선을 공용 대기열의 생성 원천으로 전환하는 기능은 구현하지 않았다. 구형 노선은 그대로 독립 실행하며 신규 반복 요청은 공용 대기열에서 별도로 설정한다. 기존 노선의 함선당 수량, 생산 재고 임계값, 운송 중 명세를 바꾸지 않고 옮기는 전환·중복 방지 규칙이 필요하므로 완료로 판정하지 않는다. 다회사 8시간 이상 장기 시험과 여러 장기 지표도 아직 검증되지 않았다.

### 재현한 기존 결함과 경계

| 사례 | 재현 및 현재 결과 |
|---|---|
| 같은 편대의 두 노선 / 빈 귀환 | 신규 테스트 `reproduces the legacy one-route constraint and empty return trip`에서 두 번째 `putRoute`가 거부되고, 첫 배송 뒤 화물 0인 함선이 기존 출발지로 이동하는 것을 확인했다. 구형 동작은 보존하며 신규 공용 작업은 편대 단일 노선 제약이 없다. |
| 목적지 포화·출발지 부족 | 구형 `full destination...`, 신규 `holds cargo...`, `competing requests...`에서 실제 화물 유지와 조건 복귀를 확인했다. 신규 작업은 배차 시 자유 재고만 예약한다. |
| 파괴·이탈·수동 명령 | 신규 `manual command...`, `returns a destroyed ship’s uncollected reservation...`, `suspends individual dispatch...`에서 적재물의 손실/회수와 출발지 미적재 예약 반환을 각각 확인했다. |
| 노선 수정·삭제 | 기존 `one-way, edit, pause/resume...`, `blocked jump paths...`는 노선 변경과 취소 시 화물과 명세를 확인한다. 신규 공용 요청은 구형 노선 수정/삭제와 연결하지 않으므로 해당 노선이 공용 작업을 암묵적으로 변경하지 않는다. |
| 같은 재고 경쟁 | 신규 `competing requests...`, `prevents legacy logistics and production...`에서 공용 요청끼리 및 생산·구형 노선과 공용 예약의 경쟁을 검사한다. 건설·조선·연구도 같은 자유 재고를 읽는다. |
| 저장 직후 중복 | 신규 저장·복원과 실제 PostgreSQL 재시작 시험에서 예약과 적재물을 분리해 확인한다. 적재 처리 중 저장, 명세 및 완료 결과를 두 번 확인한다. |
| 채굴 전용 수송선 | 채굴 명령이 유효한 편대의 수송선은 참여 요청을 서버가 거부한다. 기존 채굴 회귀도 별도 실행했다. |

## P9.8.1 데이터와 실행

- `WorldState.logisticsJobs`는 선택적 회사별 서버 데이터다. 작업 ID, 회사, 종류, 출발·목적지·품목, 수량, 0–9 우선순위, 생성/갱신 시간, 단발/반복, 상태, 담당 함선, 예약·운송 중·누적 배송·현재 반복 배송량, 손실·회수·판매 수입, 반복 완료 수와 장애/재시도 정보를 저장한다. `WShip.logisticsPool`과 `logisticsJob`은 명시적 참여와 개별 배정을 연결한다. 다른 회사 스냅샷에서는 이 필드와 작업을 감춘다.
- 단발 요청은 요청 수량을 실제 배송/판매하면 완료된다. 반복 요청은 수량을 채울 때마다 다음 주기를 만들며 플레이어가 정지 또는 취소할 때까지 계속된다. 적재량이 선박 용량보다 크면 여러 번에 나누어 처리한다. 높은 우선순위, 생성 시각, ID로 작업을 정렬하고 적합한 자사 함선 중 출발지 거리와 ID로 결정한다. 도착 가능 경로, 양방향 게이트, 정박 규격, 실제 화물 여유, 유효 명령 및 재고를 검사한다.
- 배차 시 실제 자유 재고를 원자적으로 `reserved`로 옮긴다. 이는 출발지에 남아 있는 실물의 별도 보관이며 다른 작업·생산·건설·조선·연구·판매가 쓸 수 없다. 예약은 출발지 창고 공간과 자산 평가에 포함된다. 실제 하역 장치의 적재가 끝날 때 예약에서 화물로 옮기며, 하역/판매도 실물 수량만 차감한다. 취소·수동 명령·배차 제외·적재 전 파괴는 미적재 예약을 돌려준다. 생존 함선의 기존 화물은 이동하거나 판매하지 않는다.
- 수동 개입 후 이미 적재된 분은 해당 작업의 `withdrawn`으로 기록하고 그대로 함선에 남는다. 작업의 미완료 수량은 다시 배차될 수 있으므로, 그 화물을 플레이어가 직접 같은 목적지에 전달할 계획이라면 남은 요청도 정리해야 한다. 파괴된 함선의 실제 적재분만 `lost`에 기록하며 자산을 복제해 보상하지 않는다.
- 대기열 생성·수동 제어는 재배차를 촉발하고, 완료·상태 변경 후에는 최대 5게임초의 제한된 보조 점검으로 재배차한다. 이미 배정된 작업은 더 가까운 함선이 나타나도 재배정하지 않는다. 이동·하역은 기존 전략 틱, 도킹·게이트와 물리적 화물 처리 경로를 사용한다.
- 신규 `production supply`는 지정 수량을 자사 생산 정거장으로 옮기는 명시적 요청이며 물류센터가 필요하다. 구형 노선의 생산 주문·시작/목표 재고 자동 보충 규칙을 대체하지 않는다. 건설 공급은 실제 현장 부족량에서 구형 명세와 공용 예약·운송 중 물량을 뺀다. 자동 구매, 전사 재료 탐색, 광상 재선정과 판매처 최적화는 추가하지 않았다.

## 저장 호환 및 회사 격리

구형 `WorldState.logistics`와 `Op.haul.route`는 변환하거나 덮어쓰지 않는다. 신규 필드가 없는 저장은 기존 그대로 로드하며 선택적 JSON 필드 외 SQL 스키마 변경은 없다. 동일 저장을 반복 복원해도 신규 작업을 자동 생성하지 않는다. `tests/fixtures/p971-inflight.json.gz`는 기준 커밋의 실제 코드로 만든 합성 저장이며, 적재 중인 구형 명세를 두 번 복원한 뒤 별도 공용 함선과 작업을 함께 실행하는 시험에 사용한다. 생성 스크립트는 `scripts/p981-make-legacy.ts`다.

구형 서버가 신규 예약 및 공용 작업의 의미를 이해한다고 가정할 수 없으므로, 향후 롤백은 신규 저장을 구형 바이너리에 그대로 넣는 대신 호환 백업 복원을 포함해 별도 검토해야 한다. 운영 데이터를 이행하거나 역호환을 검증하지 않았다.

## 시나리오와 자산 보존 증거

- A: 같은 편대 세 척에 서로 다른 세 목적지 요청을 주면 서로 다른 세 함선이 각각 20을 싣고 세 작업을 완료했다. 출발지·화물·목적지 합계는 500으로 유지됐다. 별도 시험에서 일반 운송·생산 공급·건설 공급 세 종류도 각각 병렬 완료했다.
- B: 한 척이 높은 우선순위 작업 뒤 다음 작업까지 자동 수행했다. 구형 노선 취소/재등록은 필요하지 않았다.
- C: 두 건설 공급 요청이 합금 15를 경쟁할 때 예약과 화물의 합계는 15였고, 저장 복원 후 배송·운송 합계도 15였다. 생산과 구형 노선은 공용 예약을 소비하지 못했다.
- D: 목적지 창고 포화에서는 20이 선내에 남았고 공간 20을 열자 자동으로 배송했다.
- E: 적재 후 수동 편제 변경은 20을 선내에 남기고 `withdrawn`으로 기록했으며 대체 선박 상실은 실제 적재 20만 `lost`로 기록했다. 적재 전 파괴는 출발지 예약을 반환했다. 신규 공용 작업의 파괴는 테스트 월드에서 함선을 직접 제거해 재현했으며 실제 전투를 통한 손실은 별도로 검증하지 않았다.
- F: 적재 처리 중의 예약과 다중 작업 운송 상태를 JSON과 격리 PostgreSQL에서 복원했다. 실제 PostgreSQL 서버 프로세스 재시작 후 두 작업은 각각 20을 한 번씩 배송했고 총량 100이 유지됐다.
- G: 기준 커밋으로 생성한 구형 명세 저장을 두 번 로드하고 기존 노선 배송 20과 신규 공용 배송 15를 함께 실행했다. 총량은 100이었다. 기존 노선은 여전히 편대를 점유한다.

## 장기 운영과 성능

`npx vite-node scripts/p981-performance.ts`는 격리된 P9 월드에서 0.25초 전략 틱을 그대로 사용했다. 정거장·함선·자금·출발 재고는 시험 픽스처이며 치안은 안전하게 설정하고 해적 출현을 껐다. 단발/반복, 같은 성계와 헬리오스행, 일부 창고 포화 및 재고 부족을 섞고 중간에 JSON 저장·복원한다. 각 규모는 240게임초 한 표본이다. 배차시간은 초기 대기열 한 번을 직접 호출해 잰 벽시간이며 서버 전체 틱은 10게임초마다 한 틱을 표본화한 수치다. ## 남은 일과 P9.8.2 연결

1. 구형 노선의 편대·운송 중 명세와 `minStock`/`targetStock`, 편도·반복·일시정지 의미를 유지하는 명시적이고 멱등적인 전환 경로와 중복 방지 검증. 신규 반복 요청이 있다는 사실만으로 기존 노선이 변환된 것은 아니다.
2. 전사적 재료 부족량·소유권·구매 거래와 공용 요청을 연결하는 P9.8.2 조달 계획. 기존 건설/생산/조선/연구 예약 및 실제 시장 재고·예산과 일치해야 한다.
3. 소스 정거장이 영구 소실되면 그곳의 미적재 예약은 작업에 보존되나 자동 반환은 해당 정거장이 돌아와야 한다. 영구 소실에 대한 별도의 자산 회수 정책과 화면이 필요하다.
4. 엄격한 우선순위에서 낮은 순위의 기아 방지, 더 큰 작업/함선 수에서의 대기열 인덱싱과 완료 이력 보존 정책, 관측 이벤트의 장기 성능을 검증한다. 긴급 선점과 다중 경유 최적화는 구현하지 않았다.
5. P9.8.3 이후의 광구 재선정, 순이익 기준 판매처, 통합 사업 계획과 다회사·위험 구역 장기 운영은 범위 밖이다.
