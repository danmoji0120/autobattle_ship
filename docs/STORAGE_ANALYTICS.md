# 공용창고 안정화와 월드 분석 개발 기록

작업 기준: 2026-11-08 1차 개발 지시서. 기존 `GROWTH_PLAN.md`의 콘텐츠 전용 Codex 역할 경계는 이번 지시서에서 명시한 시스템 작업에 한해 대체한다. P9 경제 수치와 운영 DB는 변경하지 않는다.

## Stage 1

- 구획별 첫 시간 선납 만료 시각을 `Company.leasePaidUntil`에 기록한다. 추가 구획만 새로 선납하며 이후 사용 시간을 기존 60초 운영비 정산에 합산한다. 반납은 최근 구획부터, 환불 없음. 이미 발생한 미정산 요금과 체납은 유지한다.
- 과거 선납 시각은 기존 세이브에 없으므로 추정하지 않는다. 기존 임대 수·재고·체납을 유지하고 기존 구획은 후불 누적을 계속한다.
- 자동 채굴 하역지는 정박 규격·권한·시장·품목별 구매 예산·창고 여유·거리·점프 수·자체 정거장 선호도를 적용한다. 모든 목적지가 막히면 기존 화물을 유지하고 원인·해결책을 알린다. 고정 운송 노선은 임의로 바꾸지 않고 목적지 여유가 생길 때까지 대기한다.
- 전투 회수품은 원래 하역지별 `Company.pendingLoot`에 집계하고 공간이 생기면 자동 입고한다. 개별 지급 이력을 무한 추가하지 않는다. 전투 종료 중복 실행을 차단하고, 대기 자산을 센서스·회사 자산 평가에 포함한다.
- 미완공 코어는 건설 계획의 부족 자재만 받는다. 기존 재고·예약 자재는 보존하며 코어 완공 후 기존 창고 용량을 사용한다. 새 용량·가격·보상 상수는 추가하지 않았다.

검증: 관련 4개 파일 26개 테스트 통과(243.57초), TypeScript·전체 빌드 통과. 격리된 로컬 PostgreSQL 16에서 기존 저장/마이그레이션 경합 2개 테스트 통과. 변경 전 `4a19e19` 대비 c0 1,800초·분 단위 해시 30개 일치(벽시계 기반 전투 예산 시계 고정). 브라우저 1440×900·1024×768 확인, 실제 600초 채굴→운송→하역→판매: 채굴 824.49, 판매 수입 2,801.68 cr. 재현: `node scripts/storage-browser.cjs`.

저장 영향: 기존 JSON 월드에 선택 필드만 추가한다. SQL 스키마 변경과 contentV 변경 없음. 운영 데이터 접근·반영 없음. 기능별 CPU·메모리 정량 비교는 Stage 5 통합 측정에서 보고한다.

## Stage 2–4 설계

통계는 게임 상태 밖 `SaveFile.analytics`에 저장한다. 기존 파일 저장과 PostgreSQL JSONB 저장/세대 펜스를 그대로 사용한다. SQL 마이그레이션은 필요하지 않다. 기록 시작 이전의 과거 이력은 추정하지 않는다. 관리자 계정 목록을 설정하지 않으면 멀티플레이 관리자 조회는 거부한다.
